# 节点结果预览展示调研与方案

> 状态：调研完成；推荐组合（A+B 第一步 + 输出抽屉 Diff + 画布差异徽标 + 完整结果页 Diff + 字符级高亮）已落地。
> 背景：当前画布运行完成后，每个有文本产物的节点都会在卡片底部常驻展示一段「前 120 字预览 + 摘要」。实测观感为：上下游正文重复度过高、单卡可预览的信息量又太少，输出节点还出现同一摘要展示两次。本文调研 n8n / Dify / Coze / ComfyUI 等平台的做法，并给出多套可选方案。

## 1. 当前问题

以截图中的链路「转写 → AI 校对 → AI 加工 → 输出」为例：

1. **重复内容过多**
   - 转写与 AI 校对都展示几乎相同的转写原文开头，只有字数和“校对后少 4 字”的差异。
   - AI 加工与输出展示几乎完全相同的 Markdown 开头，输出节点等于把上游内容再贴了一遍。
   - 当用户真正想确认“每一步发生了什么变化”时，看到的是 4 段相似正文，而不是 4 个不同的结论。
2. **可预览内容过少**
   - 节点宽 224–320px，正文预览被压缩到 2 行以内。
   - 预览是把全文 `replace(/\s+/g, " ")` 后截断的纯文本，标题层级、列表、段落结构全部丢失，阅读价值低。
   - 想看到完整内容必须点眼睛图标，但卡片上已经堆了一大段“看不全”的占位文字。
3. **输出节点重复展示**
   - `process.output` 在节点主体内已有“文件卡/摘要”占位（`sf-node-output-preview`），下方 `.sf-node-result` 又渲染同一份 `summary` 和正文预览，出现两次。
4. **信息层级混杂**
   - 节点卡同时承载：配置表单、运行状态、失败重试折叠区、结果预览。视觉上无法区分“这是配置”还是“这是运行产物”。

## 2. 其他平台怎么展示

| 平台 | 画布上的常态 | 结果/产物查看方式 | 可借鉴点 |
|---|---|---|---|
| **n8n** | 节点只保留状态标识（成功/失败/等待/dirty）；画布不常驻正文预览 | 点击节点，右侧面板打开该次执行的 Input/Output，支持 JSON/表格/Binary 查看；Executions 列表可加载历史执行 | 画布“干净”，数据详情放到按需打开的面板；状态用徽标表达 |
| **Dify** | 节点用绿色描边表示成功、红色表示失败；不常驻大段正文 | 节点旁“Run/Last run”弹出或打开执行详情，展示 PROCESS DATA 与 OUTPUT；变量检查器可看缓存中间变量 | 结果以“节点附近的弹层/侧栏”展示，输入与输出分区块，方便对照 |
| **Coze** | 试运行成功节点绿色描边，节点上提供查看输入/输出的小图标 | 点击节点右上角图标查看该节点的输入输出，不把正文铺在画布上 | 正文始终是“按需展开”，避免多节点同时刷屏 |
| **ComfyUI** | 图片/视觉类节点会显示缩略图小预览；文本类默认不内嵌大段文本 | 使用独立的 Preview Image / Preview Text 节点作为显式“查看器”；节点本体保持配置视图 | 预览内容按类型区分：图像给缩略图，文本给显式查看器，而不是一律塞进节点 |
| **Make / Zapier / Langflow / Flowise** | 画布/场景以状态和模块为主，结果在模块详情或运行检查器中查看 | 运行后通过模块面板、数据检查器或 Playground 查看输出 | “状态留在画布，内容留在检查器”是通用模式 |

> 结论：主流工作流产品几乎都不把“每一步的完整/长文本输出”直接常驻在画布节点上。它们通常把输出藏到**节点详情、侧栏、弹层或独立结果页**里；画布只回答“哪一步成功/失败/耗时多少/有什么产物名”。

## 3. 候选方案

### 方案 A：画布只留状态，内容全部“按需打开”（最接近 n8n / Dify / Coze）

- 去掉节点底部的 `.sf-node-result` 正文预览区。
- 节点上保留：
  - 右上角状态点（成功/失败/运行中/跳过）；
  - 眼睛图标（已有，进入输出抽屉）；
  - 一行极简元信息：`✓ 2054 字 · 3.2s` 或 `笔记.md · 5330 字`，失败时显示错误摘要。
- 把“查看完整结果”强化为：
  - 点击眼睛/节点结果图标打开右侧输出抽屉；
  - 抽屉内默认展示完整 Markdown，并提供“处理结果 / 原始输入 / 完整结果页”切换。
- 优点：画布信息密度回归“流程图”，彻底消除重复正文；每份内容都有足够空间完整展示。
- 缺点：不能像现在一样“扫一眼就看到上一步开头”；需要靠元信息/状态点吸引用户点击。

### 方案 B：类型化摘要卡（保留少量卡面信息，但预览更聪明）

不删除卡面预览，但把“统一 raw text 120 字”改为“按节点类型设计的结构化摘要”：

- **转写**：显示来源信息 + 首句摘要 + 字数。
  - `1 个音频 · 2058 字` + 第一段自然句（保留标点）。
- **AI 校对**：不再贴与转写几乎相同的开头，而是显示“变化摘要”。
  - `校对后 2054 字（较上游 -4）`，若可做 diff，再给 1 条“修改示例”；
  - 无法 diff 时只显示 `已校对 · 2054 字`，避免制造“相同文本”的错觉。
- **AI 加工 / 观点提炼**：显示 Markdown 的标题/大纲，而不是正文前 120 字。
  - 例如解析出 `# 观点提炼…`、`## 总体概要` 等，作为结构化预览。
- **合并 / 章节 / 思维导图**：显示章节数/分支数/标题列表。
- **输出**：只显示文件卡，不显示正文预览。
  - `笔记.md · 5330 字 · 点击查看/下载`；去掉下方重复的 `.sf-node-result`。
- 优点：卡面信息“少而准”，每个节点回答“这一步产出了什么变化”，不是“又复制了一遍什么”。
- 缺点：需要前端/后端增加一点摘要逻辑（解析 Markdown 标题、字数差等），改动比方案 A 大。

### 方案 C：差异/变更视角（Diff Preview）

面向“链路中间步骤高度重复”的专门解法：

- 每个中间节点不只显示自己的输出，还显示相对主要上游的变化量：
  - `转写 2058 字`
  - `校对 2054 字 · 变化 12 处`
  - `AI 加工 5330 字 · 新增结构`
  - `输出 笔记.md · 与「AI 加工」一致`
- 点击节点可进入“Diff 视图”，左右/上下对比上游与本节点，或高亮增删内容。
- 优点：把用户真正关心的“每一步改了什么”变成核心信息，重复感消失。
- 缺点：需要运行引擎或前端保存/访问上游文本；当前 `RunNodeResult` 只有自身 output，前端需要从 `run.inputs` / 图快照推导上游；Diff 算法和 UI 成本最高。

### 方案 D：悬停/选中浮层预览（保留“看得见”，但不常驻占位）

- 画布节点常态不显示正文预览，只显示状态和摘要行。
- 鼠标悬停或点击节点时，在节点附近弹出一个浮层/ Popover：
  - 头部：节点名、状态、字数/耗时；
  - 主体：渲染后的 Markdown（有最大高度，可滚动）；
  - 底部：复制 / 下载 / 打开完整结果页。
- 类似 Dify 的节点 Run 弹层，也符合 ComfyUI“显式查看器”思路。
- 优点：预览空间远大于 2 行；不会多节点同时刷屏；保留快速查看能力。
- 缺点：需要处理画布缩放时的弹层定位、遮挡、滚动等边界问题。

### 方案 E：结果模式/结果总览（把“审阅结果”从编辑画布中拆出去）

- 画布编辑态继续“干净”，运行完成后：
  - 顶部“上次结果”入口已经存在，可以把它做得更显眼，并默认进入完整结果页；
  - 或在编辑页增加一个“结果”视图切换，复用 `RunDetailView` 的布局：左侧链路输入/输出列表，右侧文档阅读，支持编辑/导出。
- 画布只保留“运行完成”和节点状态，所有正文阅读都放到专门的结果页。
- 优点：彻底分离“编辑工作流”和“审阅产物”两个任务；结果页有足够宽度做 TOC、缩放、diff、导出。
- 缺点：从画布查看中间产物要多跳一步；需要把现有结果页打磨得更易从画布进入。

## 4. 推荐组合

不推荐只做单一方案，建议按成本/收益分三步：

1. **先止血（低成本）**
   - 删除 `process.output` 节点下重复的 `.sf-node-result`；
   - 让“高级（失败重试）”默认折叠、与结果预览在视觉上分离；
   - 统一结果区为一行摘要 + 一个“查看输出”动作，不再常驻正文。

2. **再对齐主流（中成本）**
   - 采用“方案 A + 方案 B”的组合：
     - 画布常态只显示状态点和元信息；
     - 选中的节点或刚完成的节点允许展开一个结构化摘要卡（标题/字数/变化），但不显示与上游重复的正文；
     - 眼睛按钮打开抽屉看完整内容。

3. **最后做差异能力（高成本、高价值）**
   - 如果目标用户经常需要核对“AI 校对改了什么 / 输出与加工是否一致”，再实现方案 C 的 Diff 视图，并把入口放到输出抽屉和完整结果页。

## 6. 已实施记录（推荐组合 A+B 第一步）

- 画布节点不再常驻显示 `data.preview` 的 120 字正文；运行后只保留一行状态点 + 摘要元信息。
- 只有**选中且已完成**的节点会展开一段结构化摘要（保留 Markdown 换行/标题并渲染，最多约 320 字），并提供“查看完整输出”入口。
- `process.output` 节点去掉主体内重复的输出占位块，不再出现“同一摘要展示两次”；输出节点也不生成正文预览。
- `process.mindmap` 继续不生成正文预览，避免在画布上粘贴长文本。
- `previewFor` / `previewText` 改为保留原始换行后截断，选中预览不再是一行被拍平的长句。
- 输出抽屉新增「变更对比」模式：当某条输入存在 `resultText` 时，可对比「原始输入 → 处理结果」；只有一个上游输入时，也可对比「原始输入 → 当前节点输出」。对比使用轻量行级 Diff，并显示字数变化与增删行数。
- 新增 `apps/web/src/components/DiffViewer.vue` 承载变更对比视图。
- 画布节点摘要行新增差异徽标：由服务端 `node.done` 事件下发 `delta`（新生成 / 与上游一致 / 较上游 +N 字 / 较上游 -N 字 / 较上游内容变化）；运行快照恢复时前端也会根据直接上游文本重新计算。
- `RunDetailView` 完整结果页新增“对比输出”：在链路输入详情中可把“该输入/多模块合并文本”与当前最终输出做累积 Diff。
- `DiffViewer` 升级为精确字符级高亮：引入 `diff-match-patch-es`（Apache-2.0，ESM + TypeScript），对成对的替换行使用 Google diff-match-patch 算法，只高亮真正变化的字符，不再整行红/绿。
- 调研说明：`jsdiff` 虽更常用，但许可证为 BSD-3-Clause，与项目“只复用 MIT / Apache-2.0”的红线冲突，因此采用同算法族且许可证合规的 `diff-match-patch-es`。
