# 「常规」设置分组：运行与产出的默认策略

## 一、结论

设置页的「常规」从「两个孤零零的输入框」（并发数 + 输出目录）改成**运行与产出的默认策略中心**，三块：

| 块 | 设置项 | 之前的状态 |
| --- | --- | --- |
| 运行 | 并发数（1-4） | 已有 |
| 运行 | 失败自动重试次数（0-10，默认 2） | **写死在代码里**，界面无从调整 |
| 运行 | 重试等待（秒，1-60，默认 3） | 同上 |
| 产出 | 输出目录（相对或绝对路径） | 已有，但**界面从不显示它到底解析到哪** |
| 产出 | 「打开输出目录」按钮 | 新增 |
| 产出 | 文件名模板（`{project}` `{date}` `{time}` `{node}`） | 固定为工程名 |
| 运行结束提醒 | 发系统通知（开关） | **完全不存在** |
| 运行结束提醒 | 播放提示音（开关） | 完全不存在 |

默认值刻意取成与改动前完全一致（并发 2 / 重试 2 次 / 等 3 秒 / 目录 `outputs` / 文件名只带工程名 / 通知开、提示音关），
所以升级不会改变任何既有工程的产物位置与名字。

## 二、为什么这么改（问题都是量出来的，不是感觉）

### 1. 「输出目录」这个设置此前表达不了什么

`general.outputDir` 一直是「相对数据目录的子目录名」，而数据目录是启动参数，**界面里从来不显示解析结果**。
本机实测：数据目录是 `D:\Develop\scribe-flow\apps\server\data`（`apps/server/src/env.ts` 把默认值锚定在 server 包根目录），
于是成稿的实际落点是

```
apps/server/data/outputs/run_050d749b-f41e-49bc-83ce-d0911e4c1fc0/笔记.md
```

——仓库内部、中间夹一层 41 字符的运行 id。实测该目录下 27 个文件（`find apps/server/data/outputs -type f | wc -l`）。
用户想「让笔记落到我自己的文件夹」在这之前是做不到的，只能改代码或做软链接。

### 2. 运行结束没有任何反馈

改动前全仓没有 `new Notification`、没有 `Notification.requestPermission`、没有 `AudioContext`、没有 `new Audio(`，
也没有 run 级别的完成 toast（`run.done` 事件只更新节点状态与快照）。一次运行是「下载 → 转写 → AI 加工」，
几分钟到十几分钟都正常，人不会盯着画布——跑完与否全靠回去看一眼。

### 3. 重试策略写死

`apps/server/src/lib/engine.ts` 里是 `retry.maxRetries ?? 2` / `retry.backoffMs ?? 3000`（字面量）。
节点卡上可以单配（`data.retry`），模板也会写死 `{ maxRetries: 2, backoffMs: 3000 }`，
但**从调色板拖出来的节点**没有任何地方能设默认值。

## 三、关键取舍

### 3.1 输出目录允许绝对路径，顺带把一条 P0 补上

`docs/status.md` 的 P0 里原本记着：`general.outputDir` 只剥尾部斜杠，配 `..` 可写出数据目录之外，
且「数据账本这条链路已收口，engine 侧仍未处理」。这次统一收口成一个函数：

- `apps/server/src/lib/storage.ts` 的 `resolveOutputRoot(dataDir, configured)` 是**唯一**的解析点：
  绝对路径原样采用；相对路径相对数据目录解析且**不允许** `..` 爬出（爬出则回落到默认目录）；
  空值回落 `outputs`。落盘（`engine.ts` 的 `saveRunDocuments`、`process.output`）、删除（`deleteRun`）、
  账本扫描（`survey`）全部改走它，不再有第二处拼接。
- 库里记路径的规则随之明确：`toStoredArtifactPath` 在数据目录内记相对路径（与历史口径一致，老数据不用迁移），
  目录外记绝对路径；`resolveArtifactPath` 读回时两种都能解析。分隔符统一折成 `/`。
- 路由层显式拒绝「相对路径 + `..` 外爬」并说明该怎么改（`apps/server/src/routes/settings.ts`），
  而不是静默忽略——静默忽略会让人以为自己配对了。
- **绝对路径是用户显式选择**，与同一个设置页里「Obsidian 库路径」已经是任意绝对路径是同一件事，
  不引入新的风险类别；真正的风险仍是后端无应用层认证（见 status.md 的 P0），那是独立议题。

账本因此要标注：产物目录落在数据目录之外时，「输出文件」那一行的标签会变成
「输出文件（成稿 Markdown）（在数据目录之外）」——否则「合计占用」会被读成数据目录的体积。

### 3.2 重试：节点级 > 全局默认

抽成纯函数 `resolveRetryPolicy(node, general)`（`engine.ts` 导出）。抽出来的理由不是好看，
是它**可被直接断言**：要真跑出「失败两次然后成功」得先造一个会瞬时失败的节点，成本远高于收益。
不参与重试的节点类型（本地节点）恒为 0 次；`maxRetries` 为 0 是合法值，读写都不能把它当成「没传」。

### 3.3 文件名模板的边界

- 只作用于**运行收尾的自动落盘**（`saveRunDocuments`）。老工程里 `process.output` 节点自己的
  `fileName` 不走模板——那是用户显式写在节点上的名字，改它属于越权。
- 默认 `{project}`，与历史行为逐字一致。
- 模板里没写 `{node}` 而一次产出多份时，仍自动补节点名（历史行为）；补完还撞名就加 `-2`、`-3`。
  最后这层去重是刻意加的：静默覆盖掉一份产物属于硬规则第 6 条「多输入不静默丢弃」同一类事故。
- 日期取**本地时间**，不用 `toISOString()`——后者换算 UTC，东八区晚上 8 点后会得到「昨天」的文件名。

### 3.4 提醒挂在 AppLayout，不挂在画布页

运行可能从画布发起，然后用户切到结果页、切到别的工程、切到别的应用。挂在画布页只能覆盖一个页面，
所以挂在工作台外壳（`AppLayout.vue`）上看全局运行列表。

判定规则是「**上一次看到的状态是 running，这一次不是**」：

- 首屏加载时列表里早就跑完的历史运行，上一次状态是 `undefined`，不会在刷新页面时集体弹一遍；
- 新起的运行一定先以 `running` 进列表（画布 `startRun` 会立刻 `upsert`），所以不会漏；
- 已取消的运行不提醒——那是用户自己点的停止，此时人就在屏幕前，再弹一条是噪音。

同一个 run 按 id 去重（`apps/web/src/utils/run-alert.ts` 的 `notified`），因为画布页与 5 秒轮询都会看到它结束。

### 3.5 提示音用 WebAudio 现场合成

两级正弦短音（880Hz → 1320Hz，上行听起来像「办完了」），不引入任何音频资源文件：
既不用往仓库塞二进制，也不会有「音频加载失败」这种半死不活的状态。

## 五、诚实清单

- **没验证到的**：系统通知与提示音**没有在真实浏览器里跑完一次完整运行来观察**。已验证的是：
  设置页开关往返（实测点击）、权限已授予时不会被拒（实测 `Notification.permission` 为 `granted`）、
  按 runId 去重的单测、以及**判定规则本身**的单测——它被抽成 `shouldAlertRunEnd(previous, next)`
  （`apps/web/src/utils/run-alert.ts`），4 条用例覆盖「运行中→成功/失败」「首屏历史运行不补弹」
  「自己点的停止不提醒」「还在跑或终态没变」。
  但「运行跑完真的弹出一条系统通知 / 响一声」只有代码路径，没有端到端观察。用 IAB 验证这件事需要
  一次真实运行（视频下载 + 转写 + AI 调用，十几分钟且消耗额度），本次跳过了这一步——
  **这是这份文档里最该被追问的一条**。
- **已知局限**：提醒的时延取决于 5 秒轮询（画布页在时由 SSE + `upsert` 触发，基本即时）。
  理论上「起跑即完成、且画布未 `upsert`」的运行会漏报一次；实际链路里画布 `startRun` 会立刻 `upsert`，
  所以没有观察到该情况，也没有构造用例去逼它。
- **刻意没做**：深色模式（`tokens.css` 目前只有浅色令牌，element-theme 里留了骨架）；`process.output`
  节点的 `fileName` 不参与模板；AI 请求超时（`ai.ts` 的 300 秒）本轮没做成设置项——它的可调价值没有实测支撑，
  不想凭感觉加旋钮。
- **老数据**：库内既有产物路径都是相对路径，`resolveArtifactPath` 兼容，不需要迁移；
  已存的节点级 `retry` 值继续生效（节点级优先），本次改动不会改变任何既有工程的行为。
- **冒烟稳定性的一个缺口**：加了运行结束提醒之后，连续 7 次冒烟里掉过一次 55/58，事后 5 次都复现不出来，
  而且当时没抓到是哪三项失败。只找到一个可疑机制（冒烟会跑完一个工程 → 触发系统通知 → 通知抢焦点 →
  后面依赖焦点/Esc 的检查失败），**没有把它钉死**。处理是把变量去掉：夹具现在通过 CDP 把通知权限置为
  `denied` 并断言这一点，隔离后连跑 4 次 59/59。这条要按「疑似、未证实」来读。
- **模型/估算**：无。本文件所有数字都是跑出来的。
- **顺带发现的两处口径边界**（都不是本次改动引入的，也没有去修——它们属于文档门禁的计数问题，
  已补进 [AGENTS.md](../../AGENTS.md) 的「已知的边界」）：
  1. 仓库的「用例数」是静态 `it(` 声明数（`scripts/docs-gen.mjs`），而 `apps/server/src/lib/recipe.test.ts`
     用 `for` 循环生成 `it(`，于是 status.md 报的静态数比 vitest 实跑数少 7；现有守卫只拦 `.each(`，拦不住循环。
  2. 「冒烟检查项数」也是静态调用点数，脚本里有几处 if/else 两个分支各写一条 `check(`，一次只跑一支，
     所以 status.md 报 63 而脚本自报 58/58。
  本文件因此**逐处标明用的是哪个口径**。
