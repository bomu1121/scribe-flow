# 数据账本与本地数据清理（设置页「数据与工程」）

> 状态：已实现（2026-09-28）。
> 关联：[project-audit-2026-09-27.md](../research/project-audit-2026-09-27.md)（其中的媒体 GC 无全局入口、
> `graph-backups` 无入口可见两条缺口由本方案补上）。

## 1. 问题：这一页原来什么也没说

改造前「数据与工程」只有三格只读数字（数据目录 / 运行记录 / 输出文件个数）和一个清理按钮：

- `GET /api/settings/data` 只统计**产物目录**，数据目录里另外五个区域完全不可见；
- 前端 `onMounted` 里没有调 `loadDataInfo()`，只有点「刷新」才请求——页面打开时三格恒为 `—`；
- 后端返回的 `outputBytes` 从未被展示，等于算了个没人看的数。

在真实实例上量一次就知道差多少。**计量口径：界面与本文一律按字节统计、按 1024 进制显示**（下表是
2026-09-28 的实测值，给的是原始字节，避免同一个量出现两个读数）：

| 区域 | 文件 | 字节 | 界面显示 |
| --- | --- | --- | --- |
| 数据库（含 WAL / SHM） | 3 | 16,949,016 | 16.2 MB |
| 运行中间产物 `runs/` | 96 | **2,350,410,990** | **2.2 GB** |
| 输出文件（旧页面唯一统计的对象） | 25 | 391,986 | 383 KB |
| 工程图备份 | 242 | 506,325 | 494 KB |
| 媒体库 / 上传原件 | 0 | 0 | 尚未产生 / 0 B |
| **合计** | **366** | **2,368,258,317** | **2.2 GB** |

`runs/` 一项占全量的 **99.2%**，而旧页面唯一统计的输出文件只占 **0.017%**——
体积最大的地方一个字都没提。

## 2. 结论：把「看不见」变成「有数字、可回收、说得清规则」

### 2.1 账本按数据目录的六个分区计量

`数据库 / 媒体库 media/ / 上传原件 uploads/ / 运行中间产物 runs/ / 输出文件 <outputDir>/ / 工程图备份 graph-backups/`，
各自给出文件数与字节数；目录还没创建时显示「尚未产生」而不是 0。
体积换算在前端（`apps/web/src/lib/bytes.ts`），服务端只给字节。

### 2.2 五类可回收空间，每类都必须给出「多少项 + 能释放多少字节 + 按什么规则判定」

| 目标 | 判定规则 | 依据 |
| --- | --- | --- |
| `runs` | 状态不是「运行中」的运行记录，连同产物与中间文件 | 等价于原来的清理按钮，但先算出能释放多少 |
| `orphanMedia` | 媒体库里已不被任何运行引用、且不处于 `restoring` 的资产 | 审计缺口「GC 只按运行引用查找，没有全局清扫入口」 |
| `uploadOrphans` | 上传原件里不被任何媒体资产引用、且闲置超过 7 天 | `uploads/` 原本没有任何删除路径，是无上限增长 |
| `orphanDirs` | `runs/` 与产物目录下已无对应运行记录的目录与散落文件 | 删除竞态与异常退出的残骸 |
| `graphBackups` | 已删除工程的留档 + 每工程超过最近 20 份之外的历史版本 | 审计缺口「`graph-backups` 无入口可见、无清理」 |

判定规则原文随接口返回（`PruneItem.rule`），界面照抄展示——没有规则说明的清理按钮就是黑箱。

### 2.3 展示与执行共用一份 survey（关键约束）

`buildDataOverview` 与 `pruneStorage` 都先跑同一个 `survey()` 再各自取数，
所以「界面显示 5 项」与「点下去删 5 项」不可能漂移。
清理响应回报的是**实际**删除数与**实际**释放字节（失败项不计入 bytes），不是计划值。

### 2.4 清理范围必须收口在数据目录内

`general.outputDir` 是外部可改的字符串，engine 直接 `join(dataDir, outputDir)`；
配成 `..` 会让扫描与清理的作用域抬到数据目录之外（status.md 已知缺口里的路径校验问题）。
`resolveOutputDir()` 在账本入口处统一收口：越界或绝对路径一律退回 `outputs`。

## 3. 取舍与边界

- **孤立上传原件为什么要 7 天**：上传与「跑一次」之间隔着用户编画布的时间，
  只看「有没有被引用」会删掉刚上传、还没跑过的文件。7 天是「闲置」的判据，
  代价是这部分空间最长 7 天后才可回收。阈值是常量（`UPLOAD_ORPHAN_MIN_AGE_MS`），要调就改它。
- **`restoring` 的媒体资产一律不动**：下载中的资产行先于文件写入建立，
  按「无引用即孤立」判定会把正在下载的文件删掉。
- **不做本地整库导出/导入**：`docs/decisions/scribe-flow-proposal.md` 里承诺过「导出全部工程/导入工程」，
  但坚果云分组已经提供整库备份与热恢复（含工程、运行记录、设置），再做一个本地版是重复；
  这一页只留一句指路。
- **清理是破坏性的，所以自检脚本只验契约**：`scripts/m4-api-check.mjs` 只断言 400 分支，
  真正的删除路径放在临时数据目录里跑（`apps/server/src/lib/storage.test.ts`、
  `apps/server/src/routes/settings.test.ts`），不在用户的实例上做删除验证。
- **对 M4 验收档案的影响**：`docs/evidence/2026-08-28-m4-acceptance.md` 第 9 条
  「`GET /api/settings/data` 返回计数」的响应结构已被本方案替换（`runCount` / `outputFiles` 等字段不再存在）。
  该档案按规矩不改，其结论只对冻结当天成立。

## 4. 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/api/settings/data` | 账本：`totals` / `areas` / `runs` / `projects.top` / `cleanup` / `reclaimableBytes` |
| `POST` | `/api/settings/prune` | 清理，body `{ targets: PruneTarget[] }`，返回逐项的 `removed` / `bytes` / `errors` |
| `POST` | `/api/settings/reveal-data-dir` | 在系统文件管理器里打开数据目录（容器内会返回 400 并说明原因） |

原来的 `POST /api/settings/clear-runs` 已删除，能力并入 `prune` 的 `runs` 目标。
