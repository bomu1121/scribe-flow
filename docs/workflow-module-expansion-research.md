# ScribeFlow 功能工作流模块拓展 — 调研方案

> 状态：**R1 桌面研究 + R4/R5 差距分析与路线图 + M6 实施清单已完成**（2026-09-02）。R1 报告见 [r1-desktop-research.md](./research/r1-desktop-research.md)；模块拓展路线图见 [workflow-module-roadmap.md](./workflow-module-roadmap.md)；M6 实施清单见 [scribe-flow-m6.md](./scribe-flow-m6.md)。R2 产品试用（JS 站点核实）待启动。
> 关联文档：[scribe-flow-proposal.md](./scribe-flow-proposal.md)（产品定义与范围）、[ui-library-replacement-research.md](./ui-library-replacement-research.md)
> 调研原则：**先分类，后对标**——市面上工作流产品设计目的差异极大，不能拿 iPaaS 的功能清单直接套到内容加工流上；每个模块都要回答「它对 ScribeFlow 意味着什么」。

---

## 1. 调研目标

### 1.1 背景

ScribeFlow M0–M5 已完成，当前节点体系共 8 个节点：

| 类别 | 节点 | 端口 |
|---|---|---|
| 来源 | B站链接 `source.bili` | out: audio |
| 来源 | 本地文件 `source.file` | out: audio |
| 来源 | 文本 `source.text` | out: transcript |
| 处理 | 转写 `process.transcribe` | in: audio → out: transcript |
| 处理 | AI 校对 `process.refine` | in: transcript → out: transcript |
| 处理 | AI 提示词 `process.prompt` | in: transcript → out: noteBlock |
| 处理 | 合并 `process.merge` | in: noteBlock[] → out: noteDoc |
| 处理 | 输出 `process.output` | in: noteDoc\|noteBlock → Markdown |

下一步要拓展「功能工作流模块」，必须先回答三个问题：

1. 市场上各类工作流产品各自有哪些功能模块？（充分调研）
2. 哪些是 ScribeFlow 同类需求**该有但还没有**的基础功能？（遗漏）
3. 哪些是同类或近邻产品里**更高级、可差异化**的功能？（机会）

### 1.2 调研目标（可验收）

- G1：产出一份**分类竞品功能地图**，覆盖 ≥6 类设计目的不同的工作流产品、每类 ≥3 个代表产品。
- G2：产出一份**功能模块全景清单**，按统一维度拆解各产品的功能模块，逐项标注「ScribeFlow 可借鉴/不可借鉴/需改造」。
- G3：产出一份 **ScribeFlow 现状基线**（当前能力清单 + 边界），与竞品功能地图做差距分析。
- G4：产出一份**候选拓展模块长名单**，按 P0/P1/P2 优先级排序，每个模块给出「用户价值 / 实现成本 / 定位契合度 / 风险」四维评分。
- G5：产出**调研执行计划**（阶段、方法、时间、产出物），供评审后直接执行。

### 1.3 非目标

- 不把 ScribeFlow 做成 iPaaS（Zapier/n8n 式连接器平台）、BPM 审批引擎、数据管道调度器或 AI Agent 平台。
- 不复制 n8n/Dify/ComfyUI 等受许可证限制的代码；只复刻交互行为与功能语义（沿用 proposal 3.2 的红线）。
- 不做运营侧调研（定价、市场投放）；只调研功能模块。

## 2. 调研对象：按设计目的分类

> 这是本方案的核心方法：**先按设计目的分层，再在每层内做功能拆解**。同一功能（如「循环节点」）在不同设计目的下的形态完全不同——数据管道要重试与幂等，BPM 要审批与 SLA，LLM 流要上下文与工具调用，内容加工流要产物可读与逐节点预览。

### 2.1 分类框架与代表产品

| 层 | 设计目的 | 代表产品（调研必选） | 对 ScribeFlow 的关系 |
|---|---|---|---|
| L1 内容/AI 加工流 | 把素材加工成内容（笔记/文案/报告），节点=加工步骤，产物=文档 | n8n（AI 工作流部分）、Dify、Coze/扣子、Langflow、Flowise、FastGPT、百度千帆工作流、阿里百炼工作流、元器 | **最直接对标**：AI 节点、RAG、提示词块、逐节点输出预览 |
| L2 通用自动化 iPaaS | 把 A 应用事件自动接到 B 应用 | Zapier、Make（Integromat）、Power Automate、IFTTT、腾讯云 HiFlow、集简云 | **借鉴基础编排能力**：触发器、条件分支、循环、错误处理、重试 |
| L3 数据管道/调度 | 定时/依赖驱动的批流数据处理 | Apache Airflow、Prefect、Dagster、Apache DolphinScheduler、SeaTunnel | **借鉴运行引擎**：调度、重试、幂等、断点续跑、缓存、回填 |
| L4 业务流程 BPM/审批 | 人参与的流程审批与流转 | Camunda、Flowable、Activiti、钉钉/飞书/企微审批、ServiceNow | **低优先级**：人工确认节点、权限审计；整体太重 |
| L5 云服务编排 | 云资源/微服务步骤编排 | AWS Step Functions、Azure Logic Apps、Google Workflows、阿里云 FnF | **借鉴**：状态机语义、错误分支、超时控制 |
| L6 RPA/桌面自动化 | 模拟人操作桌面/网页 | UiPath、影刀、Power Automate Desktop | **低优先级**：仅「网页抓取」类节点有交集 |
| L7 DevOps/CI-CD | 构建/测试/发布流水线 | GitHub Actions、GitLab CI、Jenkins | **借鉴**：YAML 即工作流、矩阵策略、缓存 |
| L8 专业创作节点流 | 视觉/几何/渲染节点编排 | ComfyUI、Blender Geometry Nodes、Houdini、Fusion | **借鉴**：节点级缓存、显式预览、队列语义 |
| L9 垂直笔记/AI 内容工具 | 视频/音频/文稿 → 笔记 | BibiGPT、通义听悟、飞书妙记、NotebookLM、Granola、Circleback、Get笔记 | **直接竞品/近邻**：来源接入、时间轴、章节、导出 |
| L10 知识画布（非运行式） | 手动摆放的卡片与连线 | Obsidian Canvas、Heptabase、Scrintal、Milanote | **仅视觉参考**，无运行语义 |

### 2.2 每类产品的调研重点

| 层 | 必须调研的功能模块 |
|---|---|
| L1 | 节点类型（LLM/RAG/工具调用/代码/知识库）；提示词与模型管理；多模型路由；流式输出；调试与单节点重跑；子流程；对话型 vs 工作流型 |
| L2 | 触发器体系（webhook/定时/事件/轮询）；条件/循环/分支；变量与表达式；错误处理与重试；连接器数量与认证；执行历史 |
| L3 | DAG 依赖、定时调度、重试/幂等/超时、断点续跑、缓存与回填、SLA、可观测性（日志/指标/血缘） |
| L4 | 人工任务、审批、表单、泳道、权限与审计、SLA |
| L5 | 状态机、错误分支、超时、并行与等待、可视化监控 |
| L6 | 网页抓取/录制、桌面文件操作、OCR、键盘鼠标模拟 |
| L7 | 工作流即配置文件、矩阵、缓存、环境变量、密钥管理 |
| L8 | 节点级缓存、单节点执行、显式中间预览、队列与排队 |
| L9 | 来源接入（B站/YouTube/播客/会议）、转写与说话人分离、章节切分、时间轴、导出格式、分享 |
| L10 | 卡片信息密度、连线样式、画布留白 |

## 3. 功能模块全景维度（拆解统一标尺）

调研时按以下 14 个维度逐产品拆解，避免「看热闹式调研」。每个维度给出 ScribeFlow 当前的对应状态（见 §5.2 基线）。

| # | 维度 | 拆解子项 | ScribeFlow 需要回答的问题 |
|---|---|---|---|
| 1 | 编排模型 | DAG / 状态机 / 规则流 / 子流程 / 事件驱动 | 是否需要循环与条件分支？子流程是否过度设计？ |
| 2 | 节点与连接器 | 节点分类、数量、可扩展性、自定义节点 | 节点库按什么分组？何时需要自定义节点？ |
| 3 | 触发器 | 手动 / 定时 / webhook / 事件 / 消息 / 轮询 | 是否引入「定时自动运行」与「webhook 触发」？ |
| 4 | 数据流与类型系统 | 端口类型、多输入语义、变量、表达式、JSON/文本转换 | 端口类型要不要扩展（分P、时间轴、章节）？ |
| 5 | 运行引擎 | 队列、并发、重试、幂等、超时、断点续跑、缓存 | 节点级缓存能否让重跑只算变更节点？ |
| 6 | 可观测性 | 日志、审计、指标、血缘、告警 | 运行日志与节点日志的粒度够不够？ |
| 7 | 版本与协作 | 版本历史、diff、回滚、评论、多人协作 | 工程版本历史（当前只有自动保存）？ |
| 8 | 工程管理 | 模板、导入导出、环境变量、凭据、复制 | 提示词块之外的「凭据/环境变量」管理？ |
| 9 | AI 能力 | LLM 节点、RAG、工具调用、Agent 循环、多模型路由、自然语言生成流程 | 最直接的拓展区，见 §6.3 |
| 10 | 人工任务 | 审批、待办、表单 | 是否需要在「输出前」加人工确认节点？ |
| 11 | 权限治理 | RBAC、审计、SSO | 单用户自托管是否可整体后置？ |
| 12 | 开发者体验 | API、SDK、CLI、调试、单步执行、测试 | 是否提供「干跑」（不调 AI 只跑拓扑）？ |
| 13 | 发布与部署 | 环境、灰度、发布记录 | 单用户产品是否可略过？ |
| 14 | 性能与规模 | 大图性能、流式、背压、存储 | 节点数上限 200 是否够？大产物分页？ |

## 4. 调研执行方法

### 4.1 桌面研究（主方法）

- 官网与官方文档：逐产品阅读「节点/功能/定价」页，记录节点与模块清单。
- GitHub：stars、license、issue 里被高频要求的功能（反映真实需求）。
- 官方模板库：n8n workflows、Dify 模板、Coze 商店——模板里出现的高频节点即市场验证过的功能。
- 评测文章与对比视频（少数派/知乎/YouTube），重点记录「用户抱怨缺什么」。

### 4.2 产品试用（每个代表产品 1–2 小时）

- 注册并跑通一个官方模板，只试功能模块，不测性能。
- 试用记录模板：产品名 / 版本 / 日期 / 试用场景 / 发现的模块 / 交互亮点 / 可借鉴点 / 不采用原因。
- 建议至少试用：n8n（云版）、Dify（云版）、Coze、Make、Flowise；其余以文档调研为主。

### 4.3 竞品功能拆解打分

按 §3 的 14 个维度，对 L1/L2/L3 层产品做 0–2 分评分（0=无，1=基础，2=成熟/高级），形成功能矩阵热力表。

### 4.4 社区与用户评价

- G2 / Capterra / Product Hunt：看用户好评与差评关键词。
- 各产品 GitHub issue 的 `feature request` 标签：统计高频需求。
- 中文社区（知乎/V2EX/即刻）里对「视频转笔记」类工具的功能吐槽。

### 4.5 内部需求对齐

- 用 ScribeFlow 的 4 个内置模板作为场景基线，对每个候选模块做场景验证：**能否放进「视频→笔记」或「文稿→对照笔记」的链路里说得通？**
- 若仓库/用户反馈里有需求记录，一并纳入。

### 4.6 调研记录与产出规范

- 所有原始记录存入 `docs/research/`（或调研分支），引用来源 URL 与访问日期。
- 功能模块清单统一用 §3 的 14 维标尺归档，禁止散落在聊天记录里。

### 5.2 ScribeFlow 现状基线

| 维度 | 现状 | 差距信号 |
|---|---|---|
| 编排模型 | 纯 DAG，无分支/循环/子流程 | 条件分支（如「无文稿时跳过校对」）可能缺失 |
| 节点 | 8 个固定节点，无自定义节点 | 节点类型少，扩展机制未定义 |
| 触发器 | 仅手动运行 | 无定时、无 webhook |
| 数据流 | 端口类型：audio / transcript / noteBlock / noteDoc；多输入=按序合并 | 缺少结构化数据（JSON/列表）与变量 |
| 运行引擎 | 拓扑排序、并发 2、SSE、重跑、强制结束 | 无重试策略、无节点缓存、无断点续跑 |
| 可观测性 | 运行记录、节点状态、日志弹窗 | 无工程级运行统计 |
| 版本协作 | 自动保存 + 导出 | 无版本历史/diff |
| 工程管理 | 模板、导入导出、提示词块库 | 无凭据管理、无环境变量 |
| AI 能力 | 转写、校对、提示词加工、自定义提示词块 | 无 RAG、无结构化抽取、无多模型路由、无 AI 生成流程 |
| 人工任务 | 无 | 「输出前确认」是否需要？ |
| 权限治理 | 单用户自托管 | 可整体后置 |
| 开发者体验 | API 自检脚本、类型校验 | 无干跑模式 |
| 性能 | 节点数 ≤200、大产物按需加载 | 尚可 |

### 5.3 差距分析初筛

#### A. 疑似遗漏的基础功能（同类需求该有）

1. **条件分支节点**：按文稿长度/语言/是否含文稿决定走哪条加工链（L2/L5 标配）。
2. **定时/自动运行触发器**：订阅的 B 站合集更新后自动转笔记（L2/L3 标配）。
3. **失败重试策略**：AI/ASR 超时自动重试 N 次，当前只支持手动重跑（L2/L3 标配）。
4. **节点级缓存/断点续跑**：长链路中途失败，重跑不必从头转写（L3/L8 标配）。
5. **章节切分节点**：长视频转写后自动切章，输出带目录的笔记（L9 近邻标配）。
6. **文本工具节点**：查找替换、正则、模板渲染、字数统计等（L2 标配的数据转换）。
7. **导出到第三方**：Notion/飞书/剪贴板（proposal P1 已列入，仍需调研优先级）。
8. **运行统计与对比**：两次运行 diff（proposal P1 已列入）。

#### B. 高级功能机会（可差异化）

1. **RAG/知识库节点**：基于用户自有笔记库做「结合我的历史笔记」加工（L1 标配高级能力）。
2. **结构化抽取节点**：把转写稿抽成 JSON（观点/术语/行动项），再渲染成笔记（L1）。
3. **多模型路由/对比节点**：同一文稿走多个模型/提示词，自动选优或对照（L1，ScribeFlow 模板三已具雏形）。
4. **自然语言生成流程**：说「把这个视频转成技术拆解笔记」自动搭节点图（n8n/Dify 2025+ 方向）。
5. **人工确认节点**：输出前人工改稿再导出（L4 借鉴，轻量化）。
6. **时间轴节点**：转写稿带时间戳，笔记可跳转原视频（proposal P1 已有，需节点化）。
7. **子流程/模板片段**：把「校对+观点提炼」打包为可复用片段（L2/L5 的模块化）。

## 6. 差距分析与优先级评分

### 6.1 四维评分规则（每维 1–5 分）

| 维度 | 评分依据 |
|---|---|
| 用户价值 | 对「素材→笔记」核心链路的使用频率与收益 |
| 实现成本 | 相对 M0–M5 现有架构的增量成本（1=极低，5=很高） |
| 定位契合 | 是否强化「内容加工画布流」而非泛化为 iPaaS/Agent 平台 |
| 风险 | 复杂度膨胀、许可证、外部依赖稳定性 |

### 6.2 优先级公式

- 初筛排序：`(用户价值 × 定位契合) / (实现成本 × 风险)` 降序。
- 再经 MoSCoW 校准：P0 = Must（下个里程碑就应讨论），P1 = Should，P2 = Could/Won't。

### 6.3 关键判断原则

1. **先补基础，再追高级**：重试、分支、文本工具属于「同类产品的默认能力」，缺失会被用户认为产品残废；RAG、自然语言生成流程属于高级差异化，但成本与风险高。
2. **触发器要克制**：定时触发适合「订阅更新→自动转笔记」，但会引入后台调度与凭据存储；若只做「手动跑」，触发器可以整体后置。
3. **循环与子流程需警惕**：内容加工链路以线性+并行为主，循环/子流程会显著抬高图模型复杂度（schema、执行引擎、UI 都要改），除非调研证明高频。
4. **RAG 与 Agent 是定位分水岭**：引入知识库/Agent 会把 ScribeFlow 拉向 Dify 路线；调研要明确「我们做的是笔记加工，不是 LLM 应用平台」。

## 8. 风险与注意事项

1. **许可证红线（延续 proposal 3.2）**：n8n（Sustainable Use）、Dify（附加条件）、ComfyUI（GPL）只可复刻交互行为与功能语义，不可复制代码；Langflow/Flowise 非 enterprise 部分（MIT/Apache-2.0）可读源码。调研记录中必须标注每个模块的「参考来源 + 许可证状态」。
2. **设计目的漂移**：最容易犯的错是把 n8n/Zapier 的功能清单搬过来，把 ScribeFlow 做成通用自动化平台。每个候选模块必须通过 §6.3 的定位闸门。
3. **数据时效**：竞品功能迭代快，本底稿的 stars/节点数等数据需在调研执行时重新核实，所有结论标注访问日期。
4. **调研不等于开发**：本文档只产出调研方案与路线图建议；具体模块的图模型/UI/引擎改动需另立实施文档（如 proposal 的 M6+ 里程碑）。
