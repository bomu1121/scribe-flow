## 0. 结论摘要（TL;DR）

1. **有条件的收益**：多步链对「长稿 + 高保真 + 强结构」类加工（长转写稿的观点提炼/拆解、长稿分章、导图骨架）有实证支撑的质量收益；对短稿校对、轻量提炼等简单任务没有收益，反而纯增延迟与成本。
2. **不能把收益默认押在「多轮反思」上**：自反思类迭代（Self-Refine 等）质量增益存在明显的边际递减与少量样例劣化，必须配「迭代上限 + 确定性退出条件」，否则是成本黑洞。
3. **真正拉开差距的三件事**：① 步骤间**确定性校验门**（断言 + JSON 契约 + 失败定点重跑）；② 长稿的**分块 map-reduce**（解决长上下文利用率与长生成后段质量衰减，这是 ScribeFlow 素材的真实痛点）；③ 把「块」从一段纯文本提示词升级为**声明式配方**（步骤序列、可复用、可版本化）——正好命中「沉淀/复用高级加工方法」的动机。
4. **推荐落点：L1 声明式配方 + 步骤运行时，先做 1 个内置试点配方做 A/B**，默认保留现有「单次调用快路径」。不推荐现在就做节点内动态规划/半 agent 化（L4）。
5. **收益必须用证据验收**：建 5–10 条真实素材评测集，单次 vs 配方同素材双跑，人工盲评三维度（信息完整 / 忠于原文 / 结构可读），达到通过线（建议 ≥ 6/10 优于且无显著劣化）才把配方写进模板/设为默认。

## 1. 现状事实基线（代码锚点）

| 事实 | 锚点 | 含义 |
|---|---|---|
| `process.refine` / `process.prompt` 执行器：逐输入一次 `chatCompletion(system=提示词块/覆盖/兜底, user=输入文本)` | `apps/server/src/lib/engine.ts` L953-988 | 节点内没有任何子步骤、没有中间产物 |
| AI 调用层：固定 `system+user`、`temperature 0.3`、单请求 300s 超时、无多轮/无流式 | `apps/server/src/lib/ai.ts` L24-41 | 「步骤化」需要在这一层之上加编排，而不是改模型接口 |
| `process.chapter` / `process.mindmap`：一次调用要求纯 JSON，随后解析并做**上限/结构约束**（章节数、分支数、深度、节点文本长度） | `engine.ts` L1059-1119 | 已存在「输出契约 + 解析 + 约束」雏形，是校验门的最自然前身 |
| 节点级重试已存在：attempts、`node.retry` 事件、可重试错误类型集合 | `engine.ts` L796-839、L31 | 步骤级失败可直接复用同一套重试语义 |
| 节点级缓存未实现（检索无 fingerprint/cached 实现） | `engine.ts` | 步骤缓存要等 M7 缓存落地后顺带扩展 |
| 提示词块 = 纯文本 system prompt（含固定输出格式/方法论/行为边界），有 series/version/recommended 字段 | `packages/shared/src/prompt.ts` | 复杂加工方法被压进一大段文本：难编辑、难复用其中某一环 |
| 运行日志 kinds：`input / ai-request / ai-response / info`；运行详情已有「输入 → 输出」逐行 diff 视图 | `RunDetailView.vue` L966（DiffViewer） | 质量观测与 A/B 对比的 UI 基础设施已存在 |
| 运行态不写入工程图（设计约定），节点产物/日志走运行记录 | `README.md` 设计约定 | 节点内步骤的中间产物也应走运行记录，不进图模型 |

现状一句话：**画布级已经把「素材 → 笔记」拆成了节点工作流；但每个 AI 加工节点内部仍是黑盒单发**。本调研回答的问题是：把这一层再往下拆一层，值不值、怎么做最先进。

## 2. 收益调研

### 2.1 证据：什么情况下多步确实有收益

1. **任务可预测时，显式工作流优于 agent/单发大提示**。Anthropic《Building effective agents》的结论是：多数应用用「可预测步骤的工作流」就够，Agent 只用于步骤不可预测的场景；其中「提示链（prompt chaining）」把复杂任务切成明确子任务、每步有独立上下文；「评估器-优化器（evaluator-optimizer）」在「有明确标准、迭代能改进」时使用。其配套文章给出三条工作流模式的适用条件与代价对比——这正好是「AI 加工节点内部」的语义：素材→笔记的加工步骤是可预测的，适合显式链而非自由 agent。
2. **自反馈迭代有实证增益但有上限**。Self-Refine（Madaan et al., 2023）：同一模型自我反馈+修订，在 7 个任务上相对单次基线平均提升约 20%（绝对），但代价是推理调用量成倍增加，且部分样例不升反降、越往后收益越低——因此反思环必须「有界」（轮数上限 + 退出条件 + 防振荡）。
3. **长上下文的利用率是真实瓶颈**。Lost in the Middle（Liu et al., 2023）显示模型对长上下文中间部分利用显著弱于首尾；长文档摘要领域的研究也提示：一次超长生成中后段更易出问题。ScribeFlow 的真实输入恰恰是 5k–50k 字的转写稿——「一次读完、一次写完」在信息保真上的天花板是结构性存在的，不是换提示词能根治的，这给「分块加工再汇总」提供了证据基础。
4. **「校验器 + 可编程管道」是把方法沉淀为资产的技术路线**。DSPy 的核心理念：用程序化管道（含验证器）取代手写大提示词，模块可组合、可自动调优。对应到 ScribeFlow：加工方法不该只是一段提示词文本，而应是「步骤 + 契约 + 校验」的可复用资产——这直接命中用户「沉淀/复用高级加工方法」的动机。
5. **LLM 做评委有已知偏差**（位置/冗长/自夸偏好，Zheng et al., MT-Bench），所以步骤门控要**优先用确定性断言**（长度、必含章节、JSON schema、关键金句回原文比对），LLM 判断只做低权重辅助——这条同时是质量门控的正确姿势。

### 2.2 反方证据：什么时候多步是纯亏

| 反方论点 | 说明 | 对 ScribeFlow 的含义 |
|---|---|---|
| 延迟与成本线性累加 | N 步 = N 次调用、每步还要重传上下文 | 简单任务（短稿校对、轻量提炼）单次调用秒级即可完成，多步毫无必要 |
| 错误放大 | 上一步的幻觉/遗漏会作为事实进入下一步，且更难定位 | 步骤越多，越需要每步契约校验 + 日志可查，否则调试成本大于收益 |
| 过度加工 | 对「本来就不需要深度」的稿子做拆解-反思-重写，输出反而变啰嗦 | 需要「快路径默认 / 深路径可选」双轨，而不是整体替换 |
| 反思环边际递减、个别劣化 | Self-Refine 实证 | 迭代上限 1–2 轮即可，收敛条件优先于固定轮数 |
| 维护面扩大 | 一块文本提示词 → N 段提示词 + 步骤元数据 + 校验逻辑，UI/日志/产物语义都要变 | 配方 DSL 必须收敛到少数结构（顺序 / 有界循环 / map-reduce），拒绝任意图 |

### 2.3 收益判断矩阵（映射到 ScribeFlow 具体场景）

| 场景 | 输入特征 | 单发现状的真实痛点 | 多步链预期收益 | 建议 |
|---|---|---|---|---|
| AI 校对（refine） | 短稿为主 | 痛点不明显 | 低 | 保持快路径；长稿时才考虑分块 |
| 观点提炼 / 技术拆解（prompt，核心场景） | 5k–50k 字转写 | 长生成后段质量衰减、信息遗漏/微编造、单次失败整节点重跑 | **高**：拆解 → 分块起草 → 金句/数据回原文核对 → 格式化 | 首个试点配方 |
| 分章（chapter） | 长转写 | 一次 JSON 长输出易截断、章节结构不稳 | 中高：预分界 + 逐章 + 汇总；至少先上「JSON 契约 + 定点重试」 | 校验门先行，map-reduce 后置 |
| 导图（mindmap） | 长稿 | 一次提炼层级易漏分支、分支不平衡 | 中：分块抽分支 → 合并去重 | 同分章 |

判断：**对 ScribeFlow 的素材类型（口播转写稿 + 笔记加工目标），「长稿保真」和「结构产出」两类痛点都能从多步链获得结构性改善；但收益集中在中长稿深度加工，且必须用评测集验证后才可切换默认行为。**

## 3. 进阶实现方案（四级）

### L0 朴素顺序多步（不推荐作为方案，仅作认知基线）

把提示词块手拆成 N 条 `chatCompletion` 顺序调用，后一步拼上一步的全文。

- 缺点：无中间契约、失败无法定点、无收敛条件、成本无护栏、产物只有最后一段可审计。
- 结论：它只证明了「多步能跑」，不代表「多步值得做」。

### L1 声明式配方 + 步骤运行时（推荐落点）

**概念**：提示词块可选携带一个「配方」：有序步骤数组。没有配方的块 = 单步配方，行为与今天完全一致（向后兼容）。

```
配方示意（观点提炼，最终以评审稿为准）：
steps:
  - id: extract          # 通读全文，输出观点清单 JSON（每观点带原文依据摘录）
    expects: { kind: json, schema: 观点清单, asserts: [每观点必有依据文本] }
  - id: draft            # 按清单 + 依据起草结构化笔记
    expects: { kind: text, asserts: [必含 ## 总体概要, 观点数 == extract] }
  - id: audit            # 金句/数据逐条回原文核对，输出核对表 JSON
    expects: { kind: json, asserts: [无"未找到"条目] }
  - id: finalize         # 依据核对结果修正终稿，只输出 Markdown
    expects: { kind: text, asserts: [长度 <= draft * 1.3] }
```

关键设计点：

1. **步骤结构收敛**：`{ id, prompt（可引用 {{input}}/{{prev}}/{{all}}，分别指原文、上一步输出、全部前序输出）, model?（每步可覆盖模型）, expects: { kind, schema?, asserts[] } }`。断言全部确定性：`contains / notContains / lengthGte / jsonSchema / 引用回查（金句子串必须出现在原文）`。
2. **执行语义**：顺序执行；断言失败 = 该步失败，抛带「断言语义」的错误并允许走现有节点重试；网络/429/5xx 复用现有 `node.retry`（`RETRYABLE_NODE_TYPES` 不变）。
3. **运行可见性**：SSE 复用 `node.progress` 展示步骤进度（消息含「步骤 2/4」），新增 `node.step.done / node.step.error` 两个收尾事件；`run_node_logs` 增加 `step` 列，运行详情日志可按步骤筛选；节点摘要显示「配方 4 步 · 1 输入 · 4 次调用 · 总字数」。
4. **存储与图模型**：`prompt_blocks` 增加可选 `recipe`（JSON，zod 校验）；工程图文件不加字段——老工程、老导入导出格式不动。
5. **UI 形态（延续「操作进卡片」铁律）**：节点卡片仍是「配方/块」一个下拉 + 摘要；配方编辑放设置页块库（可参照 PromptEditorView 扩展），**不在卡片内堆步骤编辑器**，避免复刻右侧检查器复杂度。

### L2 有界收敛环（evaluator-optimizer 的受控版）

在 L1 上加一种特殊步骤：`{ mode: "reviseLoop", draft, critic, revise, maxIterations: 1–2, exitWhen: 断言通过 或 输出与上轮相同 }`。

- 每轮记录输出快照；退出后节点摘要给出「修订 1 轮 · 改动 23 行」（行级 diff 思路可复用 DiffViewer）。
- 成本护栏：迭代上限（默认 1）、输出无变化即停（防振荡）、critic/revise 可用 `model` 覆盖（草稿用便宜模型、终稿用主力模型）。
- 证据口径：Self-Refine 的边际递减说明 **1–2 轮后不值得继续**；默认 1 轮是「花一份评审钱买一份修订」，超过要用户显式开启。

### L3 长稿 map-reduce（对 ScribeFlow 价值最高的一项）

在配方里支持两类结构步骤：

- `chunk`：按标题/段落或字数窗口（含重叠）把长稿切成块；
- `map`：对每块执行一段子配方（并行度 = min(块数, 设置的引擎并发)，防止突破并发红线）；
- `reduce`：汇总各块产物 → 去重/排序/统一标题 → 终稿。

对应关系：与引擎现有语义一致——转写节点「多音频逐条处理、按序空行合并」、merge「多输入按序合并」。中间产物 = 每块的输出，全部进运行日志/运行详情（不落图）。

这是「长稿保真」问题的正解（2.1.3），同时带来副产品：失败只重跑坏块（等 M7 缓存落地后按块指纹缓存，成本进一步下降）。

### L4 节点内动态规划 / 半 agent 化（明确不做，记录理由）

步骤序列由 LLM 每次决定、内部工具调用等。

- 不做理由：① 素材→笔记的加工步骤可预测，动态化收益低；② 不可预测成本与延迟，与「运行前能预估」的产品气质冲突；③ 定位闸门——那是 Dify/Agent 平台的能力，ScribeFlow 不做；④ 评测与审计难度陡增。
- 未来若出现外部工具/知识诉求：走路线图 P2 的「Agent 接口化（MCP/OpenAPI）」把**工程**暴露出去，而不是在节点内部长 agent。

## 4. 落地路线建议

### 阶段 A：运行时原语 + 一个试点配方（默认关闭）

- 引擎：步骤事件、断言门、`prompt_blocks.recipe` 列、日志 step 维度；「观点提炼 v2」内部配方化为 4 步（extract → draft → audit → finalize），**旧块与自定义块全部按单步回退，行为零变化**。
- UI：节点卡片显示配方名与步骤数；运行详情日志按步骤分组。
- 验收口径：schema 校验通过；无 recipe 块跑出与今天逐字一致的结果（回归）；单步 recipe 与多步 recipe 都可在 3 个模板中端到端跑通；步骤日志/事件可见。

### 阶段 B：A/B 评测（决定配方是否转正的关键闸门）

- 建 5–10 条真实语料评测集（真实转写稿优先，覆盖短/中/长与不同口播风格）。
- 同一素材跑「单次块」与「试点配方」，产物成对盲评三维度：信息完整 / 忠于原文 / 结构可读。
- 通过线（建议）：≥ 6/10 素材配方明显更优、且无素材显著劣化 → 配方转正并进模板；否则只保留为「高级选项」或回炉。

### 阶段 C：配方库化（承接「沉淀/复用」动机）

- 设置页配方管理：内置配方只读、自定义配方可编辑步骤（步类型受限于顺序/有界循环/map-reduce 白名单）。
- 步骤级缓存：等 M7 节点缓存指纹落地后，指纹粒度下探到步骤/块。
- 模板升级：把验证过的配方写进新模板与内置块推荐版本（沿用 series/version/recommended 机制）。

## 5. 风险与红线

| 风险 | 对策 |
|---|---|
| 定位漂移：滑向「AI 编排平台」 | 配方 DSL 锁死三种结构；节点仍是一颗加工节点；L4 明令不做 |
| 成本/延迟失控 | 每配方声明步数与预计调用数，运行前节点摘要可见；迭代上限与模型覆盖是配方的一等字段 |
| 复杂任务反而更差（错误放大/过加工） | 双路径默认快；断言门 + 人工盲评闸门（阶段 B）后才允许转正 |
| 评测缺失下拍脑袋切换默认行为 | 阶段 B 通过线是硬门槛；旧模板/旧块永不隐式改语义 |
| UI 复杂度回潮（卡片塞步骤编辑器） | 配方编辑放设置页块库；卡片只做选择与摘要 |
| 导入导出/老数据破坏 | recipe 为可选列，zod 宽松兼容；图文件格式不变 |
| 许可证 | 只借鉴 n8n/Dify 等「子步骤/反思」的产品语义，不复刻代码（沿用项目红线） |
