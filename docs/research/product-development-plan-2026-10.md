# 后续开发方案：从证据链到知识闭环（2026-10）

> 触发：要求在不继承历史展望的前提下，重新理解项目并给出后续开发方案。本文以 2026-10-19 的源码、本机 `apps/server/data/scribe-flow.sqlite` 与 `data/runs` 为准，不采用 `docs/` 里的历史待办或里程碑。数字口径见文末「诚实清单」。

**结论：下一步最值得投入的不是再加节点，而是把「证据链」和「增量执行」做成底座。** 具体说，先做三件事：**转写资产化**（带时间戳/说话人、可复用）、**长文稿分段执行**（不再整篇塞给模型）、**结果可修订**（编辑能落盘并被下游使用）。这三件做完，检索、问答、复习、批量生产才有稳定的数据基础。

---

## 一、代码视角的现状

### 已经很强的部分

这个项目真正的壁垒不是「节点多」，而是三套别处很少同时具备的能力：

1. **证据链**：`packages/shared/src/trace.ts` 要求引文逐字命中原文；`apps/server/src/lib/traceExternal.ts` 会抓取外部来源正文并再次逐字校验；`apps/server/src/lib/recipe.ts` 有 JSON 根键、引用回查等断言门；`material-staleness.ts` 还能发现「换了素材却只重跑下游」。
2. **Obsidian 知识操作**：frontmatter、标签词库、相关笔记回补、溯源笔记与普通笔记互链、坚果云同步，这些不是简单导出 Markdown。
3. **可测量性**：每次外部调用都记 token/音频秒数，金额按用户单价估算；`compare.ts` 有机械指标与行级 diff；当前工作区 `pnpm typecheck` 通过，76 个测试文件、891 条用例全部通过。

这些是应该继续放大的东西。

### 真正的缺口

| 代码事实 | 证据 | 影响 |
| --- | --- | --- |
| **转写只有纯文本，没有时间戳和说话人** | `apps/server/src/lib/ai.ts` 的 `TranscribeResult` 只有 `{ text, usage }`；`bilibili.ts` 没有字幕接口；`TraceSourceRef.locator` 只是自由文本 | 引用无法跳回视频那一秒；提示词要求「区分说话人」但没有说话人标签可依据；溯源报告里的定位容易变成模型自述 |
| **长文稿没有分段，也不检查截断** | `engine.ts` 的 `runNode` 把整段 `text` 直接传给 `chatCompletion`；请求体不读 `finish_reason`，也不设 `max_tokens` | 本地实测最长转写 111,966 字，p50 5,780、p90 14,635；长视频可能被模型静默截断，或直接超上下文 |
| **没有内容寻址缓存** | 媒体资产只服务 `keepVideo`；`data/runs` 实测 559.7MB，其中 149.4MB 是重复内容（26.7%）；111 次运行里 71 次是 `fromNode` | 重复运行会重新下载、重新转写、重新调模型；多输入节点失败重试会从第 1 个输入重来 |
| **结果页编辑只支持复制，不落盘** | `RunDetailView.vue` 的 `toggleEdit`/`resetDraft`/`copyMarkdown`；`routes/runs.ts` 没有保存输出的接口 | 人工校对无法回流；没有「AI 原文 vs 人工修订」；下游重跑永远用 AI 原文 |
| **队列在浏览器内存里，且一个工程只能跑一个** | `stores/run-queue.ts` 明确写「刷新页面即失」；`createRun` 拒绝同工程第二个 running | 刷新丢队列；无法排批、无法定时；服务重启后没有作业恢复 |
| **数据库没有迁移机制，服务没有应用层认证** | `db/client.ts` 是手写 `CREATE TABLE IF NOT EXISTS` + 逐列 `ALTER TABLE`；`app.ts` 只有本机 CORS 门，没有 token 认证 | 新增转写/修订/索引表风险高；把服务放到 NAS 或局域网前必须先补认证 |
| **失败会级联，但错误不告诉你下一步** | 本地库里 52 次 `process.transcribe` 报「没有可转写的音频输入」，182 个节点因「上游失败，跳过」 | 用户看到的是「转写没输入」，而不是「上游来源没跑成功，请先跑来源节点」 |

说明：本地 111 次运行中有 65 次 error，但这个库包含大量开发调试运行，**不能当成线上失败率**。它只能说明失败形态。

## 二、外部对标：学什么，不学什么

| 外部能力 | 公开资料里的做法 | 对 ScribeFlow 的判断 |
| --- | --- | --- |
| **NotebookLM：源绑定 + 逐条引用 + 拒绝回答** | 公开资料显示它强调「只从上传的来源回答」、行内引用指向原文/时间点，并支持思维导图、闪卡/测验等 | **学**：引用必须可回查、资料没有就明确说没有。**不学**：音频/视频概览这类高成本生成，和文字笔记主线关系弱 |
| **BibiGPT：字幕、时间戳、思维导图、多平台** | 官方 `llms.txt` 明确写「字幕、重点、思维导图、可导出笔记」；搜索摘要另称支持时间戳、Obsidian/Notion 导出、批量与 API（未在官方页逐条确认） | **学**：字幕快路 + 时间戳 + 批量。**不学**：30+ 平台适配，维护成本会吃掉核心功能 |
| **Snipd / Podwise：高亮、时间戳、说话人、复习、Obsidian/Notion 导出** | Snipd 官方页明确写高亮片段、AI 摘要、说话人识别、导出到 Notion/Readwise/Obsidian 等；Podwise 的公开资料强调逐字稿、时间戳、思维导图、导出（页面本次网络不可达，来自搜索摘要） | **学**：把「引用」升级成可跳转的高亮；把「练一练」接上复习队列。**不学**：移动端耳机快捷捕捉，和桌面画布不是一条产品线 |
| **n8n 2.0：HITL、子工作流、队列、发布状态** | 官方 2.0 breaking changes 明确：子工作流因等待 webhook/表单/HITL 恢复时，父工作流会拿到子工作流结果；队列模式、发布/取消发布也有变化 | **学**：持久队列、可恢复的人工审核状态。**不学**：通用工作流平台/插件市场，ScribeFlow 的竞争力在领域节点和证据链，不在通用性 |
| **WhisperX / FunASR：时间戳与说话人分离** | WhisperX 官方 README 写词级时间戳、pyannote 说话人分离、faster-whisper 批量推理（large-v2 官方称 70x realtime），BSD-2；FunASR README 写中文 ASR、时间戳、说话人分离流水线、VAD/标点、离线/边缘运行，工具包 MIT（模型权重单独授权） | **学**：做可选的本地转写 sidecar，优先 FunASR 的中文能力；云端 ASR 保持默认。**不学**：把 Python/模型权重硬塞进 Node 主进程，Windows 安装摩擦会毁掉体验 |

## 三、产品主张

**把 ScribeFlow 从「一次性生成笔记的画布」变成「可重复生产、可核对、可复习的本地知识流水线」。**

三条原则：

1. **证据优先**：每条主张都要能回到原文的某一句、视频的某一秒；不能回查的内容，宁可标成「未核实」。
2. **本地优先**：转写、索引、修订、队列都落在本机 SQLite 与文件系统；云端模型只是可选算力，不是数据归宿。
3. **异步人工**：人不是流水线里的阻塞节点。AI 先跑，把低置信、引用缺失、质量异常的结果放进「审核箱」，人有空再改。

一句话版本：**每条结论回到原视频那一秒；每次重跑不重复花钱；每篇笔记能被修改、检索、复习。**

## 四、路线图

| 阶段 | 主线 | 关键交付 | 验收数字（可测） | 估算 |
| --- | --- | --- | --- | --- |
| **P0** | 可信输入与增量执行 | 迁移机制、转写资产库、长文分段、产物去重、失败可行动 | 同素材二次运行 ASR 调用 = 0；111k 字长文不截断完成；重复产物从 149MB 降到 <10MB；每个失败都有下一步 | 3–5 周 |
| **P1** | 时间锚点与证据笔记 | ASR 分段/说话人、字幕快路、播放器联动、引用→时间戳校验、质量报告 | 100% 段落有 start/end；≥90% 引用能定位到时间戳；点击引用到播放 <300ms；字幕命中率实测 | 4–6 周 |
| **P2** | 人机协作与知识闭环 | 修订落盘、审核箱、FTS 搜索、带引用问答、练一练复习、提示词评测 | 修订跨刷新保留且下游可用；1 万篇笔记搜索 p95 <100ms；问答引用逐字命中；不可答问题明确拒绝 | 6–8 周 |
| **P3** | 批量生产与平台化 | 持久队列、定时/追更、节点级模型与预算、指标看板、API/MCP | 服务重启队列不丢；定时触发误差 ≤1 分钟；50 条批量逐条可追踪；打标成本降 ≥30% | 4–6 周 |

> 估算口径：1 人 + AI 辅助的开发时间，**模型估算**，不含调研、返工和本地 ASR 模型下载/调试。

### P0：可信输入与增量执行

**1）先补迁移机制，再动表结构。**
新增 `schema_migrations(version, name, applied_at)`，把现有 `ALTER TABLE` 收进有序迁移；启动时先备份数据库再迁移。验收：用旧库副本跑迁移，工程、运行、标签数据零丢失。

**2）转写资产库 + 内容寻址缓存。**
新表：

- `transcripts(id, source_key, content_hash, engine, model, language, duration_sec, text, segments_json, usage_json, created_at)`
- `transcript_segments(transcript_id, idx, start_ms, end_ms, speaker, text)`

缓存键至少包含：源内容哈希 + ASR 引擎/模型/语言 + 是否说话人分离 + 适配器版本。命中时引擎记 `usage.calls = 0`，界面明确写「复用 2026-10-xx 的转写，本次 0 元」，并提供「强制重新转写」。

**3）长文稿分段执行。**
不要给每种节点各写一套截断逻辑，做一个统一的 `longTextPipeline`：

- 有分段/时间戳时按段切；没有时按段落/字符预算切。
- 每块 6k–8k tokens（估算，CJK 按 1 字≈1 token 保守估），10% 重叠。
- Map：逐块产出结构化笔记 + 引文 + 时间范围；Reduce：合并、去重、保留引用。
- 每块落库，失败可从第一块缺失处续跑，不重付已完成块。
- 检查 `finish_reason`；截断时明确失败或继续分段，不静默交付半篇。

验收：用本地那条 111,966 字转写跑通；引用覆盖率 ≥90%；成本相对单次整篇调用上升不超过 20%，或质量提升可量化。

**4）产物去重与清理。**
新运行共享音频资产（B 站按 bvid+cid、文件按内容哈希）；旧运行不强行搬迁，走现有 `prune` 清理。验收：当前 559.7MB 中可回收的 149.4MB 重复内容有明确报告；删除前 dry-run 列出引用，不误删。

**5）失败可行动。**
给 `RunNodeResult` 增加 `errorCode` 与 `nextAction`。例如「上游没有可用产物」→ 按钮「先运行来源与转写」；「未配置 ASR 密钥」→ 按钮「去设置」。验收：20 条固定失败用例，每条都有人能执行的下一步。

### P1：时间锚点与证据笔记

**1）ASR 返回分段，而不是一段字符串。**
把 `TranscribeResult` 扩成 `{ text, segments?, usage }`，兼容旧适配器。云端优先用支持 `verbose_json`/分段的接口；不支持时退回纯文本，界面标「无时间戳」。

**2）可选本地转写 sidecar。**
不要把 Python 塞进 Node。做一个独立进程/HTTP 服务，优先 FunASR（中文、VAD、标点、说话人分离），失败时自动回退云端。设置页做「检测本地引擎」而不是自动下载几 GB 权重。WhisperX 作为备选，但其 pyannote 说话人分离需要 Hugging Face token，安装门槛更高。

**3）字幕快路。**
B 站有字幕时优先取字幕，YouTube/播客用可选 `yt-dlp` 或 RSS 字幕；支持导入 SRT/VTT。命中字幕时跳过 ASR，直接得到带时间戳的段落。验收：对 20 条视频统计「字幕命中率」和「每小时成本节省」，用实测决定是否扩大平台支持。

**4）引用变成可点击的时间。**
笔记、溯源报告、练一练里的引文都带 `start/end`；B 站链接拼 `?t=`，本地视频用现有 `MediaPlayer` seek；没有视频时显示时间戳文本。结果页增加「逐字稿」视图：按说话人分组、搜索、点击定位。

**5）引用→分段校验 + 质量报告。**
现有 `recipe.ts` 的引用回查从「在整篇原文里找」升级为「在该时间窗的分段里找」。每个产物记录：

- 引文校验通过率
- 带定位的引用占比
- 重复行比例
- 结构指标（标题/列表/表格，复用 `compare.ts`）
- 本次成本与缓存节省

在「对照」视图里并排展示，让提示词选择从「感觉哪版好」变成「哪版引用覆盖高、成本低」。

### P2：人机协作与知识闭环

**1）修订落盘。**
新表 `note_revisions(id, run_id, node_id, parent_id, origin, text, created_at)`；`run_node_results` 增加 `current_revision_id`。结果页「保存修订」后，下游 `previousOutputs` 必须优先读当前修订；同时保留 AI 原文，支持 diff 与「恢复 AI 原文」。验收：刷新后修订还在；从下游节点重跑时用的是修订文本，有测试钉住。

**2）审核箱。**
不阻塞流水线。低引用覆盖、高重复、校验失败的产物进入审核箱；用户批量看 diff、改、批准。定时/批量运行尤其需要这种异步模式，而不是 n8n 那种阻塞式 HITL。

**3）稳定的笔记身份。**
现在同名默认退让成 `(2)`、`(3)`。给「来源 + 提示词 + 目标目录」一个稳定 note id，提供 `新建 / 更新 / 追加` 三种发布策略；默认仍可保持「不覆盖」，但重复运行不再无声堆副本。

**4）本地全文检索。**
用 SQLite FTS5 索引 Obsidian 库与运行产物。中文分词先做 spike：FTS5 默认 tokenizer 对中文不友好，优先验证 `trigram` 或字符 bigram；1 万篇笔记 p95 <100ms 再继续。搜索结果显示标题、片段、标签、来源、时间。

**5）带引用的问答。**
检索 top-k（先 FTS，不急着上向量库）+ 模型回答；回答必须返回结构化引用 `{notePath, heading, quote, timestamp?}`，服务端逐字校验 quote 存在，校验失败就降级为「资料里没有」。验收：30 条固定问题，引用全部可命中；不可答问题不编造引用。

**6）练一练接复习。**
持久化 `drill_sets` / `drill_attempts`，用简单间隔重复（先 SM-2，后续可换 FSRS），先做「今日复习」和 Anki CSV 导出，不做完整 Anki 插件。

**7）提示词/配方评测。**
复用「全提示词对照」模板：同一素材跑多版提示词，记录质量指标、成本、耗时，存在 `run_quality` 表。验收：同一输入同一提示词两次运行，机械指标完全一致；A/B 在 10 条素材上给出可复现的差异。

### P3：批量生产与平台化

**1）持久队列。**
服务端 `jobs(id, project_id, type, payload_json, status, run_at, attempts, lease_until)`。交互式单次运行可继续用现有前端队列；批量/定时走服务端队列，刷新不丢，重启可恢复。仍然保留「一个工程一个运行」的互斥。

**2）定时、追更、批量。**
`B 站收藏夹/合集/RSS/文件夹监听 + watermark`：只处理新增项；定时任务带「本次新增 N 条」摘要。这是 BibiGPT/Podwise 的批量能力，但落在本地画布上。

**3）节点级模型与预算。**
`process.obsidian` 打标用便宜模型，`process.prompt` 终稿用强模型；节点可覆盖模型、配置 fallback。每个运行可设预算上限，超出前暂停并让用户决定，而不是跑完才发现花了钱。

**4）指标看板。**
运行成功率、失败原因分布、p50/p95 耗时、每个工程成本、缓存命中率、引用校验通过率。全部从现有 SQLite 出，不引入外部遥测。

**5）API/MCP（可选）。**
当前 REST 已经覆盖大部分能力，但没有认证。先补 token + HTTPS，再考虑 MCP，让 agent 能创建运行、查询笔记、读取引用。不要在没有认证的情况下暴露到局域网。

## 五、首批 6 周的具体顺序

| 周 | 做什么 | 产出 |
| --- | --- | --- |
| 1 | 迁移机制；`transcripts`/`transcript_segments` 表；缓存键设计；长文基准脚本 | 旧库可迁移；能记录一次转写的分段与用量 |

| 3 | 长文分段 Map/Reduce；截断检测；2 小时视频跑通 | 111k 字不截断；每块可续跑 |

## 六、动手前先做的四个验证实验

1. **长文基线**：拿本地 111,966 字转写，跑当前单次调用，记录是否截断、耗时、token、输出长度；再做分段原型，在 5 条长素材上比较引用覆盖率与成本。**若分段后质量没有提升、成本还涨 >20%，先不要全量上线。**
2. **时间戳价值**：3 条视频、每条 10 条引文，测「从笔记找到原视频那句话」的耗时：无时间戳 vs 有时间戳。**若中位耗时下降不到 50%，先只做时间戳文本，不做播放器联动。**
3. **缓存收益**：同一工程连续跑两次，记录 ASR 调用、AI 调用、耗时、费用；再打开缓存跑两次。**若二次运行的时间/费用下降不到 30%，说明瓶颈不在缓存，先去查下载和模型排队。**
4. **编辑需求**：在本地加一个匿名计数器，记录「进入编辑态」「复制编辑结果」的次数。**如果编辑态使用率很低，修订/审核箱可以往后放；如果很高，P2 提前。**

这四个实验都不需要改产品架构，先做测量，再决定投入。

## 七、明确不做的清单

- **不再新增垂直节点**（阴阳师攻略这种）。垂直需求用「提示词 + 配方 + 输出模板」表达，节点类型保持在通用能力层。
- **不做 30+ 平台适配**。B 站、本地文件、文本、字幕是主线；YouTube/播客用可选 `yt-dlp`/RSS，不承诺全平台。
- **不先上向量数据库**。先把 FTS5 检索 + 逐字引用校验做好；向量检索是召回增强，不是引用可信的替代品。
- **不做音频/视频概览生成**。成本高、和文字笔记主线弱相关。
- **不做通用工作流平台/插件市场**。子工作流、插件 SDK 会稀释领域优势；先把领域节点做深。
- **不做阻塞式人工审核**。定时/批量运行里，阻塞审核会让整条流水线停摆；用审核箱异步处理。
- **不在没有认证的情况下做远程访问/多用户**。本地 CORS 门不等于认证。

## 八、诚实清单

- **方法**：以源码、`apps/server/data/scribe-flow.sqlite` 和本地 `data/runs` 为准；没有做用户访谈，也没有把 `docs/` 里的历史展望当依据。
- **本地数据局限**：111 次运行里 65 次 error，但包含大量开发调试；失败率不能当线上指标。转写长度统计基于 22 条已完成转写，样本不大。
- **实测数字**：71,269 行源码、16 种节点、76 个测试文件/891 条用例、当前工作区 typecheck 与测试通过；`data/runs` 559.7MB、重复 149.4MB；最长转写 111,966 字、p50 5,780、p90 14,635。以上都是本轮实际读取/运行得到的。
- **模型估算**：各阶段工期、token 换算、成本节省比例是估算，不是实测；落地前用上面的四个实验校准。
- **外部资料局限**：NotebookLM/Podwise 官方页本次网络不可达，相关能力来自搜索摘要；BibiGPT 官方 `llms.txt` 只确认了字幕/重点/思维导图/文件导出，时间戳与 Obsidian/Notion 导出来自搜索摘要，需以产品页为准。WhisperX/FunASR/n8n 的结论来自各自官方 README/文档。
- **未验证**：没有实现任何新功能原型；编辑「只复制不落盘」的结论来自 `RunDetailView.vue` 与 `routes/runs.ts` 的代码检索，未逐条点击所有 UI 路径。FTS5 中文分词效果、FunASR 在目标机器上的实际速度和显存占用，都需要先做 spike。
