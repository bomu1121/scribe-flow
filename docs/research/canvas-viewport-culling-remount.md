# 视口裁剪的副作用实测：B 站来源卡片「拖出视野再拖回」会重解析一次

> 触发：用户把画布拖到 B 站来源卡片离开视野、再拖回来，卡片里的封面/标题/合集列表全没了，
> 变成「正在解析视频信息…」；追问「目前这个设置你觉得很合理吗」。
> 这条不是新隐患——**开视口裁剪那次（`onlyRenderVisibleElements`，`FlowCanvas.vue`）的调研里已经点名过**。
> 那份文档（当时放在 `docs/research/` 下，文件名 `canvas-performance-optimization.md`）后来按
> 「撤掉合成基准叙事」删掉了，原文可用 `git show b5b06b5` 查到：
>
> > 裁剪会带来节点组件的反复挂载/卸载……本项目在这里有一个具体隐患：`ScribeNode.vue` 的 `onMounted`
> > 会在卡片带 `url` 时发起一次 B 站解析并把远端值 patch 回工程图。节点滚出视口再滚回来就会重新挂载
> > → 可能重复发请求、重复写图。**我在基准图里没有 B 站卡片，所以这一点没有验证**
>
> 这份文档就是那次的「补验」，并给出修复后的对照。

## 0. 结论

**不合理的是卡片、不是裁剪。** 裁剪本身是有依据的优化（200 节点时 DOM 8926 → 2099，官方文档也写了
「平移会让节点反复挂载/卸载」这个代价）；不该发生的是**卡片把「已解析的结果」只放在组件本地 ref 里**——
卸载即丢，于是重挂载只能重新走一遍网络。

修复后同一段操作：**重新挂载后 0 帧内容不完整、0ms 恢复、预览请求净增 0 次**。

## 1. 机制（先确认再用）

1. 画布开了 `onlyRenderVisibleElements`（`apps/web/src/components/canvas/FlowCanvas.vue`）。
2. 节点滚出视野 → Vue Flow **卸载**该节点组件（实测：DOM 里 `.vue-flow__node` 数量 1 → 0）。
3. `ScribeNode.vue` 里这份解析结果（封面/标题/上传者/分P/合集列表）存在组件本地 `ref` 里，
   与工程图无关（工程图只留了 `bvid/title/cover/uploader/duration/pageInfo/items`）。
4. 拖回来 → 重新挂载 → `onMounted` 再次 `schedulePreview(url)` → 500ms 防抖 + 一次
   `POST /api/videos/preview` → 卡片在这段时间里没有任何内容可显示。

## 2. 实测（CDP，离线可复现）

口径：**真 Chrome（headless）+ 真实页面 + 真实平移**，但在页面里拦掉 `/api/videos/preview`，
返回一份固定的「1 个视频 + 109 集合集」数据（形状照 `packages/shared/src/video.ts` 的 `VideoPreview`），
并给这次应答加 **120ms** 人为延迟。这样测的是**前端**的行为，不打 B 站、结果可复现。
逐帧录制放在页面里做（`requestAnimationFrame` 环路），因为 CDP 往返本身就有几十毫秒，抓不到那几帧。

| 读数 | 改前 | 改后 |
| --- | --- | --- |
| 拖出视野后节点是否被卸载 | 是（`.vue-flow__node` = 0） | 是（同左，裁剪未被关掉） |
| `/api/videos/preview` 请求数（拖出→拖回） | **1 → 2（净增 1）** | **1 → 1（净增 0）** |
| 重新挂载后「内容不完整」的帧数 | **38 帧 / 192 个已挂载帧**（全部是「正在解析」转圈帧） | **0 帧 / 193 个已挂载帧** |
| 从重新挂载到内容完整 | **627ms**（转圈从第 0 帧起持续 610ms） | **0ms**（第 0 帧即完整：封面、标题、109 行选集） |

## 3. 改法

- 新增 `apps/web/src/utils/bili-preview-cache.ts`：**进程内**缓存链接解析结果，键是链接原文（去首尾空白），
  TTL **5 分钟**、上限 **30 条**——与后端预览缓存（`apps/server/src/routes/videos.ts` 的
  `PREVIEW_CACHE_TTL` / `PREVIEW_CACHE_MAX`）同口径，所以客户端命中时最坏也只是比「真的再请求一次」
  旧同样的时长，不会更长。
- `ScribeNode.vue` 的 `schedulePreview` 先查缓存：命中就同步落到卡片，**不发请求、不进 loading**。
- 把「解析结果落到卡片」抽成 `applyPreview(url, result)`，缓存命中与请求回来共用一份——
  否则两条路径各写一遍，勾选状态会在重挂载后和首次解析不一致。
- `patchChanged()`：只把真正变了的字段写回工程图。

## 4. 顺手修掉的第二条（同一段代码）

**链接解析在飞时把输入清空，转圈会永久卡住**（不是本次报的现象，但在同一个函数里）：

- 机制：`schedulePreview` 复位 `previewLoading = true` 后，请求的 `finally` 只在 `seq` 未变时关它；
  输入被清空时 `seq` 已加、新链接又是空的直接 `return`——于是没人负责关这个转圈。
- **对照实验（单变量）**：把这行复位（`previewLoading.value = false`）单独去掉再跑，
  清空输入 1.6s 后 `loading: true`（永久转圈）；加回来是 `loading: false`、卡片回到空态。
- 触发条件是「改链接的 500ms 防抖窗口内清空」，所以是稳定复现，不是偶发。

## 5. 复现步骤

```
# 1) 起服务：pnpm dev（web :5173 / server :8787）
# 2) 建一个只含一个 source.bili 节点的临时工程（改 URL 为任意 BV 链接）
# 3) CDP 打开 http://localhost:5173/project/<id>，注入 fetch 拦截：
#    - POST /api/videos/preview → 返回固定合集数据（120ms 延迟），并计数
#    - PUT  /api/projects/:id/graph → 计数 + 记录请求体（viewport / bvid / title）
# 4) 页面内起 rAF 环路，每帧记录：节点是否挂载、是否在转圈、有没有封面/标题/选集行
# 5) 用鼠标事件把画布向左拖到节点完全离开视野 → 确认 .vue-flow__node 归零
# 6) 拖回来 → 录 2.5s → 统计「内容不完整帧 / 恢复耗时 / 请求净增」
```

## 6. 诚实清单

- **只有一次会话内的读数**：改前/改后各跑了 1 次完整脚本（改后为确认稳定性共跑了 3 次，读数一致）。
  没有做多轮统计、没有算方差；样本是 1 个节点、1 个（假）视频、109 集合集。
- **假数据不是真 B 站**：`/api/videos/preview` 被拦掉并返回固定数据，所以这份文档**不测**后端解析质量、
  不测真实网络时延。120ms 是人为加的（比真实往返快，因此这里 610ms 的转圈时长是**下限**：
  真实场景还要加上真实往返）。用户截图上的那 500ms 防抖 + 真实往返，只会更长。
- **`patchChanged` 省下的那次「重复写图」没能量出来**：单变量对照（把 `patchChanged` 临时改成无条件
  `patch`）发现，重挂载的写入与平移产生的 viewport 写入落在**同一个 500ms 防抖窗口**里被合并成一次 PUT，
  所以它省下的是「把工程图标脏」，不是一次可观测的请求。请求体逐条核对：修复后那 3 次 PUT 的
  viewport 两两不同、都对应平移保存视图这条设计内路径，没有一次来自重新挂载。
- **缓存只在内存里**：刷新页面即失效（这是刻意的——运行态不进工程图，见仓库约定）。TTL 5 分钟内
  视频标题/合集列表的变化不会体现；与后端缓存同口径的取舍。
- **只动了 `source.bili` 这一条路径**：`SourcePickerDialog.vue`（粘贴链接建工程）仍然直连接口，没接这份缓存；
  其它节点类型里也没有同类「挂载即请求」的卡片（逐个看过 `node-cards/` 与 `ScribeNode.vue` 的挂载逻辑）。
  结果预览浮层（`previewOutput`）是悬停/点击才取的一次性内容，卸载丢失不影响阅读——没有动它。
- **换过来源之后的第一下仍会解析一次**：在合集里点「切到这一集」（或切分P、链接被写成规范形式）时
  链接换成了新的一串，缓存键跟着变、必然 miss 一次，那一下还是会有转圈；之后这个新链接就在缓存里了。
  没有把「本地推导出来的那半份预览」也写进缓存——它带着一组自己拼的 `pages`，写进去会让之后对同一
  链接的解析看起来「少了分P」。**这一条没有实测**（本次脚本测的是「同一个链接」这条路径）。
- **没有回归门禁**：「拖出视野再拖回」这条路径**没有自动化断言**。`pnpm smoke:ui` 不在 CI 里，
  且往门禁脚本里加用例与「自研门禁总行数只降不升」冲突，所以本次证据是一次性 CDP 脚本（上面第 5 节）。
  新增的自动化只有缓存本身：`apps/web/src/utils/bili-preview-cache.test.ts` 7 条（`pnpm test` 跑）。
- **裁剪本身没有重新评估**：这次没有重测 200 节点下的 DOM 数量与帧率，也没有试「关掉裁剪」的对照。
  理由：关掉裁剪换回的是已经量过的性能收益，而问题出在卡片的状态归属，改卡片是更小的改动。
