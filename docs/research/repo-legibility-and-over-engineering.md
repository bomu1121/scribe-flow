# 仓库可读性与过度工程：外部证据与本仓处置建议

这份调研回答一个问题：**一个仓库要怎么做，才既能让 AI 工具读懂它，又不会滑向过度工程？**
起因是一次很具体的失败：一个 agent 被要求"以技术分享评委会问什么"来评审本项目，
结果它交出来的问题清单几乎全部来自本仓自己的 `status.md` 缺口表和分享稿的"没做好的三件事"——
它把仓库的自我批评叙述当成了项目的问题清单，而没有去看产品本身。这不是模型能力问题，是仓库信号设计问题。

## 0. 三条结论（先读这段）

1. **上下文文件（AGENTS.md 这类）不是"写得越全越好"，而是"只写推断不出来的"。** 有对照实验：
   LLM 自动生成的上下文文件让任务成功率**下降**、成本**上升 20% 以上**；人写的只在冷门仓库上有
   约 **+4%** 的边际收益，且仍要付出最多 **19%** 的额外成本。架构综述式的内容被明确证明**无效**。
2. **指令密度与上下文长度本身就在降分。** 500 条指令的密度下最强前沿模型只有 **68%** 遵循率；
   长上下文会一致性地让性能下降，而且**语义相近但无关的内容会主动诱发错误**——
   一个仓库里"看起来相关"的元文档正好属于这一类。
3. **时序类信息（现状、进度、验收快照、计划）不该进 `docs/`。** 这是文档工程界的共识做法；
   它们该进 issue / PR / CI 产物 / commit。本仓恰好把这四类全放进了 `docs/`，
   于是它们既会腐烂，又会成为 agent 注意力最强的信号源。
4. **最危险的一条：任何以权威口吻写的文档，都会关掉 agent 去核对的冲动。** 有对照实验显示，
   拿到一份过期权威文档后，agent 主动核对隐藏依赖的比例从约 **100%** 掉到 **0–33%**，
   被"积极误导"的比例达 **68–100%**，任务成功率跌到 **0–32%**；
   而更反常的是：**换成一份新鲜的文档，核对率同样被压住**。
   结论是文档并非"补充信息"，它**替代**了 agent 自己去查证的动作，过期与否只决定它停下核对的那件事是真是假。
   这正好解释了本仓的处境：`status.md` 是一份口吻确定、缺陷密度很高的权威文档，
   agent 读到它之后就不会再去问"这些缺口是不是这个项目真正的重点"。

## 1. 证据一：上下文文件到底有没有用（有对照实验）

**一手来源**：*Evaluating AGENTS.md: Are Repository-Level Context Files Helpful for Coding Agents?*，
Gloaguen 等（ETH Zurich / LogicStar.ai），arXiv:2602.11988，2026-02。
我从原文摘要直接抓到的表述：

- 上下文文件"**generally do not improve task success rates**"（大体上不提升任务成功率）；
- 推理成本平均上升"**over 20%**"；
- 文件里的指令确实被"**well followed**"（模型照做了）——
  这正是反直觉处：**照做了，但没用，还更贵**；
- "repository overviews"（仓库综述）虽然流行且被模型厂商推荐，但**被证明没有帮助**；
- 结论：上下文文件的价值在于**说明非标准的编码实践**，任何"为了提升表现"的改动都应该先被严格评测。

**二手来源**（搜索摘要转述，我未取到原文全文，引用时请当低一档证据）：
分条件数字为 LLM 生成文件 −3% 成功率 / +20% 以上成本；人写文件在 AGENTbench（138 个任务、
12 个"冷门仓库"）上 +4%，在 SWE-bench Lite（300 个热门仓库任务）上约为 0；
人写文件成本最多 +19%；GPT-5.2 与 GPT-5.1 Mini 的推理 token 分别多 **22%** 与 **14%**；
仓库专有工具调用从 0.05 次升到 2.5 次。作者给的操作判据是：

> 逐行问自己：**"删掉这一行，agent 会不会在某个它自己发现不了的地方失败？"** 不会就删。

同源的实践案例（二手）：某项目把根 `AGENTS.md` 从 **127 行压到 26 行**，只留"踩过的坑"，
把流程清单挪进 skills、把可通过 `--help` 发现的内容整段删除。

**对本仓的直接推论**：`AGENTS.md` 的 9 条硬规则不是等价的——
第 2 条（颜色只用令牌）由 `lint:ui` 机器强制，写在文件里属于"重述 CI 已管的规则"，是最该删的一类；
第 3/4/5 条（组件不自研、画布交互不自研、许可证只复用 MIT/Apache-2.0）恰恰是 ETH 论文里
**值得写**的"非标准实践"——推断不出来，且是法律/架构约束；
第 9 条（每次回复以目标对照表结尾）是纯仪式：它让每一轮 agent 输出变长（成本），
但对任务正确性没有任何作用，属于"指令被勤勉执行但无收益"的教科书样例。

## 2. 证据二：指令密度、上下文长度，以及权威文档对核对本能的抑制

**IFScale**（arXiv:2507.11538，Distyl AI，2025-07，一手摘要）：
500 条关键词包含指令、20 个前沿模型、7 家供应商，最佳前沿模型在 500 条密度下**只有 68% 遵循率**；
存在三种退化曲线（阈值型 / 线性 / 指数型）、**偏向靠前指令的偏置**与若干类错误模式。
（二手转述补充：有综述把"约 3000 token / 30–40 条有效指令"当作临界点，
并以此解释 Claude Code 把 `CLAUDE.md` 控制在约 200 行的设计取舍。此条我未取到一手原文。）

**Context Rot**（Chroma，2025-07，一手报告，我直接抓到了数字）：

- 测 **18 个模型**（Anthropic / OpenAI / Google / Alibaba 各家）；
  "**Across all experiments, model performance consistently degrades with increasing input length.**"
- **distractor 效应**：单个 distractor 就让表现低于基线，4 个叠加进一步下降；
  失败分析里 distractor 2 和 3 最常出现在幻觉答案中——即**相似但无关的内容不是"被忽略"，而是主动致错**。
- **结构化反而有害**：打乱的 haystack 一致性地**优于**逻辑结构化的 haystack，
  报告原话是 "**structural coherence consistently hurts model performance**"。
- **聚焦 vs 全量**：LongMemEval 306 条 prompt，全量 prompt 平均约 **113k token**，
  聚焦版约 **300 token**，聚焦版分数显著更高。
- 位置效应：唯一词出现在**靠前**位置时准确率最高。

**对本仓的直接推论**：本仓有一份 40 个文件、交叉链接完备、带 front matter 与生命周期分类的文档集——
从"工程审美"看它很整齐，但从上面的证据看，**结构化的完备语料对模型是负资产**：
它提供大量语义相近（都"很像项目说明"）却与当前任务无关的内容。
`status.md` 里的 P0/P1/P2 缺口表尤其典型：它长度可观、缺陷密度高、语气紧迫，
对任何"说说这个项目有什么问题"的请求都是最强的注意力磁铁——上一轮 agent 的表现正是这个机制的产物。

### 2.1 权威文档会抑制核对行为（这条最能解释本仓的现象）

**来源**：surface-bench（预注册对照基准，"Does documentation accuracy change LLM-agent performance?"）。
我**未取到论文原文**，以下为搜索摘要转述。设计是"只变文档块"的单变量对照：
C0 只有代码 · C1 过期文档 · C2 新鲜文档 · C3 过期文档 + 漂移报告 · Cw 过期文档 + "可能已过期"的泛泛提醒；
多轮工具循环（只给读文件 / grep / 列目录，所以 agent **有能力**自己核对）；确定性判分，共 3250 次评分。

摘要转述的结果：

- 过期文档下，agent 被"**积极误导**"的比例达 **68–100%**，任务成功率跌到 **0%（GPT-5.4）到 32%（Opus）**；
- 换成新鲜文档，成功率回升到 **94–100%**；
- **不给文档时**，五个模型都会去打开那个隐藏依赖（约 **100%**）；一旦给了过期文档，
  核对率崩到 **0%（GPT）** 与 **约 20–33%（Claude）**；
- 最反直觉的一条：**新鲜文档同样压制核对行为**。作者的意思是，
  文档并不在信息层面帮到 agent，它**替换掉了 agent 去核对的直觉**。

**这条证据的强度要打折**：该基准的作者就是漂移检测工具 Surface 的开发者，存在利益冲突
（作者自己承认，并用"预注册假设 + git 标记的分析计划"缓解）。所以它只能当**方向性证据**。

**对本仓的直接推论**：这是上一轮跑偏最准确的解释。`status.md` 以确定口吻
（"**这是 ScribeFlow 唯一的现状权威来源**"）列出 P0/P1/P2 缺口，agent 读完便不再问
"这些缺口是不是这个项目真正的重点"。问题不在于它写错了——它写的每一条我都核过是真的——
而在于**它的存在本身就替代了"去核对这个项目到底在做什么"这个动作**。

## 3. 证据三：时序类信息不该进 `docs/`

文档工程社区（含 Diátaxis 的多个实践变体）收敛出一条与本仓冲突的规则——
**不要放进 `docs/` 的东西**：状态报告、进度更新、测试/基准结果、会议纪要与决策记录、
带日期的计划、时点快照。它们各自的正确定位是：

| 不该进 docs/ | 该去哪 |
| --- | --- |
| 进度、状态 | issue / 看板；或 README 里的一小段 |
| 测试与基准结果 | CI 日志、release 产物 |
| 决策记录 | commit message（或极少数不可逆决策的 ADR） |
| 带日期的计划 | issue / milestone |
| 时点快照（验收档案） | release 说明、CI artifact |

**llms.txt 的反面教训**（二手，多来源一致）：Ahrefs 对 13.7 万个站点的统计显示约 **97%** 的
`llms.txt` **零请求**；Limy 对 5.15 亿次 AI 机器人请求的分析中只有 **408 次**命中 `/llms.txt`。
真正被 coding agent 大量读取的是**干净的 markdown 副本**，而不是索引文件。
共识是：**坏的/过期的这类文件比没有更糟**。

**对本仓的直接推论**：本仓 `docs/` 下正放着这五类里的四类
（`status.md` 现状、`plans/` 带日期计划、`evidence/*-acceptance.md` 时点快照、`CHANGELOG.md` 进度），
并且额外用 `content_hash` 冻结机制把它们固化下来。这与"用派生内容代替手写内容"的正确做法方向相反——
可取的恰恰是本仓**已经在做的另一半**：`docs-gen` 的生成块（数字从源码推导）。
判断标准很简单：**这份内容能不能从源码/测试里推出来？** 能就生成，不能且会腐烂的就别进仓库。

还有一个本仓命中率很高的子问题：**引用性腐烂**（referential rot）——文档里写的是
"某个文件的某一行定义了某东西"，而那个东西早已搬走。有一项针对 AI 配置文件的实证研究
（arXiv:2606.09090，"Context Rot in AI-Assisted Software Development"，二手转述）专门统计这类
"引用了已不存在的代码元素"的情况。本仓的 `status.md`、`docs/evidence/*`、分享稿页脚都大量使用
`文件:行号` 形式，而且本仓**自己已经意识到**这件事——`docs-lint` 的 R12 就是为了校验它而存在的，
但它只覆盖 `docs/`，不覆盖 `sharing/`。这属于"机制对了、覆盖没跟上"。

## 4. 证据四：流程债务与"单人项目的仪式"

- **流程债务**（二手，多来源）：定义是"曾经有用、现在只在消耗精力的仪式、工具与规则"。
  最锋利的自检问句是：**"如果我们今天是全新的，这套做法里有哪几条我们不会重新做出来？"**
- **仪式的成本**（二手）：一个 4 人团队算出 Scrum 仪式占容量约 **9.4%**（含上下文切换后实际 15–20%）；
  另一例是给 3 人团队加 4 个仪式、在 8 周交付期里花掉 **90 个工程小时**（2 周以上）。
- 最著名的一句：**"The Best Process Is No Process. Unless you're more than 1 person in a team."**

**对本仓的直接推论**：本仓是单人项目、立项一个月。它有 12 条文档规则、20 条以上自研 lint 规则、
2142 行门禁脚本、8 字段 front matter schema、`content_hash` 冻结与显式重冻流程、
以及 57 个文档文件。上面那条自检问句的答案大概率是"文档门禁与验收冻结不会重做"。

## 6. 处置建议：删 / 移 / 留 / 加

**留（不可推断、且能长期不腐烂）**
- 面向人与 agent 的导向性说明（本仓的 `docs/deploy.md` 属于这一类）：推断不出来，也不会随代码变动而腐烂。
  注：写下这份调研时的仓库里还有 node / usage / architecture 三份同类文档，当前的 `docs/` 里没有它们，
  所以"这三份该留"的结论在本仓库落不到实处。
- `docs-gen` 的生成块机制：**这是本仓最该保留的发明**——数字从源码推导而非手写，是"派生内容"的正确形态。
- `AGENTS.md` 里第 3/4/5 类规则（架构与许可证约束）：这正是 ETH 论文认为值得写的那一类。
- `CHANGELOG.md`：时序信息的正确容器。

**移（同一内容换个不会腐烂的容器）**
- `status.md` → 压成 README 的一节（"当前进度与已知缺口"），或直接进 issue。
  它不是"文档"，是一张待办表；而待办表在 issue 里有天然的生命周期。
- `docs/evidence/*-acceptance.md` → 验收时点快照移到 CI artifact / release 说明。
  它们"永不修改 + 内容指纹"的性质，说明它们本来就不是活文档。
- `docs/plans/*` → issue / milestone。
- `docs/decisions/*`（14 份）→ 只留真正不可逆的选型（如 UI 框架替换、sharing 这类长期约定），
  其余让 commit message 承担。

**删（只服务自己、没有第二读者）**
- `content_hash` 冻结与 R6、以及"改了要显式重冻"的摩擦流程——它的唯一消费者是它自己。
- 12 条文档规则里的形式类规则（R1 front matter 完备性、R7 数字禁写、R11 class 与目录一致、R12 行号可解析）：
  如果文档集缩小到十来份，这些规则维护成本会高于收益。
- `AGENTS.md` 第 9 条（每轮回复以目标对照表结尾）：纯仪式，只会让每一轮输出变长。
- 反 slop 规则里属于"口味"而非"缺陷"的条目（例如全局禁 `scrollIntoView`、全局禁任何 emoji）：
  它们会把"这个项目的约定"污染成一大堆噪声指令；风格问题应该留在 linter 的私有偏好里，
  而不是写成会被 agent 认真执行的硬规则。

**加（把"可发现"这件事做对）**
- `AGENTS.md` 收敛成一张**不可推断清单**，逐行用那句判据筛：删掉它，agent 会不会在它自己发现不了的地方失败？
- 把契约留在代码里：`packages/shared/src/schema.ts` 的 Zod 校验 + 测试，本身就是最不易腐烂的"文档"。
  这一条有外部证据支持：有研究用**构建与测试产物**（组件、依赖、测试覆盖）生成一张确定性的
  架构图给 agent 用，在 8 个仓库 × 3 个商业 agent 上得到平均 **+12.2% 准确率**与 **−53.9% 完成时间**，
  且在最复杂的场景收益最大；另一项研究显示，只给轻量的**调用/继承拓扑**就能改善函数级定位
  约 **+2.2pp** 并缩短轨迹，而密集标签反而要多花约 **9.9%** token。
  也就是说：**结构性信号（构建、测试、依赖图）比散文式说明更有用**。
- 如果确实还需要一处"当前状态"，用生成块（已有机制），而不是手写叙述——
  本仓的 `docs-gen` 正是"派生而非手写"的正确形态，应保留并扩大它的比重。

对比度复算和门禁覆盖盲区。这个来源结构恰好印证了第 2 节的机制：仓库里最强、最系统的信号
是它自己的元叙述，agent 会优先继承它。

更准确地说，这不是"我读了文档所以被误导"，而是第 2.1 节那条：
**一份口吻权威的缺口清单，会取消 agent 去核对"这个项目真正在做什么"的动作**。
我当时确实核对了很多东西（行数、常量、对比度），但核对的**全部是那份文档给出的题目**，
没有去质疑题目的选取本身。

## 8. 诚实清单

- **一手 vs 二手的界线**：第 1 节的分条件数字（−3%/+4%/+19%/+22%/+14%、AGENTbench 138 任务、
  SWE-bench Lite 300 任务）来自搜索摘要而非论文全文，**只能当低一档证据**；
  我从一手原文取到的只有"大体不提升成功率""成本 +20% 以上""综述无效""指令被良好遵循"这几条。
  第 2 节的 IFScale 临界点（约 3000 token / 30–40 条）同样是二手。
- Chroma 报告的数字为**一手抓取**（18 模型、distractor 叠加、结构化有害、113k vs 300 token）。
- 第 4 节的流程债务数字（9.4%、15–20%、90 小时）均为**二手转述**。
- 第 2.1 节 surface-bench 的全部数字均为**二手转述**，且该基准的作者是待测工具（Surface）的开发者，
  **存在利益冲突**（作者以预注册与 git 标记的分析计划缓解，并主动声明）。请当方向性证据使用。
- 第 6 节引用的两项结构信号研究（构建/测试产物生成的架构图 +12.2% 准确率与 −53.9% 完成时间；
  轻量调用拓扑 +2.2pp、密集标签 +9.9% token）同样是**二手转述**，我未取原文。
- 第 3 节末尾的"引用性腐烂"（arXiv:2606.09090）也是**二手转述**。
- **文献时效**：本轮检索到的若干论文（含 ETH 的 AGENTS.md 评测、surface-bench、RIG 等）
  在搜索结果里呈现为 2026 年的预印本，其中一部分可能是**尚未定稿的 forward-dated preprint**。
  正式引用（例如放进分享材料）之前，请回查 arXiv 页面确认版本与数字。
- 第 5 节的仓库数字为**本次实测**（在工作树 2026-09-27 的状态上）；行数用 `wc -l` 与按行分割
  两种口径会有个位数差异（例如画布目录 `wc -l` 是 5687，按 `split("\n")` 是 5700，
  差在文件末尾有无换行）。
- 第 6 节的处置建议是**我的判断**，不是实验结论；其中"14 份 decisions 只留少数"这类建议
  取决于你打算让仓库承担多少"可回溯性"，那是个产品决策而非工程事实。
- 我**没有**做的：没有实际评测"删掉这些文档后 agent 表现如何"。若要把这件事从推测变成实测，
  正确做法是造一组任务（例如"给画布加一种新节点"），在"现状仓库"与"瘦身后仓库"下各跑若干次，
  比成功率与步数——这也正是 ETH 论文对"任何改动都该被严格评测"的要求。
