# 双维度知识库：按「UP」与按「议题」检索

要回答的两个问题：

1. **某个 UP 对他分析过的各种事情，分别持什么观点？**
2. **某个议题上，各个 UP 分别持什么观点？**

这两问是同一份数据的两个切面（facet）。本文先给结论，再给现状实测（读码得到），
再给目标存储结构与分期落地方案，最后是诚实清单。

> 口径说明：本文所有「实测」指**本次会话内读源码与 grep 得到的静态事实**（无端到端运行、无 API Key、无真实 vault）。
> 涉及 Obsidian 行为的结论标注为「调研」——来自官方文档与社区实践，**未在本机 vault 里跑过**。
> 没有一项数字来自运行数据，不要当成性能或效果指标使用。

## 1. 结论（先看这段）

**现状：只做了半个维度，而且是做不到聚合的那半个。**

- **UP 维度：有，但不稳。** 「Obsidian 笔记」节点会把 UP 主名字写进 front matter 的 `作者:` 字段
  （`apps/server/src/lib/engine.ts` 的 `case "process.obsidian"` 与 `upstreamSourceMeta` 配合，
  名字源自来源节点的 `uploader`）。但只存**名字字符串**、不存 B 站 mid，
  **UP 改名或同名就会静默断链/错并**。
- **议题维度：没有。** 现行 front matter 里没有任何议题字段。AI 只提取 `人物 / 事件 / 时期`
  （`extractHistoryEntities`，历史向），标签只来自节点手填的 `tags`。
  仓库里确实设计过受控词表（`settings.ts` 的 `DEFAULT_TAG_TAXONOMY`，含「领域 / 概念」类目）
  和 AI 打标器（`RunEngine.buildObsidianTags`），但**打标器是死代码**：全仓 0 个调用点，只有定义。
- **「观点」这一层完全没有被结构化。** 内建提示词块「观点提炼」其实已经产出「观点块」
  （`packages/shared/src/prompt.ts` 的 `PROMPT_GUANDIAN`：现象/背景 + **作者的判断** + 论据 + 边界/反方），
  但它是**Markdown 正文**——机器读不到，两个切面都白搭。

**最佳存储方式（结论）：**

1. **一篇笔记 = 一个视频**（不是一次运行、不是一次加工），front matter 里同时带
   `UP` 与 `议题` 两个维度，且**都写成 wiki 链接**（`"[[某某UP]]"` / `"[[某议题]]"`），不写裸字符串。
2. **两个维度各有一篇「实体笔记」（hub）**：`UP/某某UP.md` 与 `议题/某议题.md`。
   切面查询就是打开这两篇 hub 看它聚合出来的表。
3. **查询用 Obsidian 内置的 Bases**（v1.9+ 核心插件，2025-05 上线），Dataview 只做兜底。
   Bases 只读 YAML front matter，**不认正文里的行内 `key:: value`**——这正是必须把元数据写进 front matter 的硬理由。
4. **真正的「观点库」要第三层**：把「作者的判断」抽成**原子观点卡**
   （一篇一条观点，属性：UP / 议题 / 立场 / 断言 / 出处视频 / 出处时间）。
   只靠视频笔记带两个属性，只能回答「他讲过哪些议题」，回答不了「他对该议题的观点是什么」。
5. **绝不用文件夹做这两个维度。** 文件夹是单父级结构，天然承载不了两个维度；
   社区共识（含 Obsidian CEO kepano 的做法）是**笔记放平，分类靠属性里的双向链接**。

## 2. 现状实测：产物到底怎么落盘的

### 2.1 有两条落盘路径，用途完全不同，但共用「输出目录」一个概念

| 路径 | 触发 | 写到哪 | 内容 | front matter |
| --- | --- | --- | --- | --- |
| **运行收尾快照** | 每次运行成功 | `<输出根目录>/<runId>/<渲染文件名>.md` | 叶子节点产物原文 | **无** |
| **Obsidian 入库** | 「Obsidian 笔记」节点 | 设置里的 vault（或坚果云远端） | 包装后的笔记 | **有**（10 个可能字段） |

前者是 `RunEngine.saveRunDocuments`（`apps/server/src/lib/engine.ts`），目录拼的是 `join(outputRoot, active.id)`
——`active.id` 是 `run_xxx`，**每次运行一个新目录**。文件名模板 `general.fileNameTemplate`
（默认 `{project}`，见 `packages/shared/src/output.ts`）。它写的是**纯 Markdown，不加任何 front matter**。

后者是 `case "process.obsidian"`。现行 front matter 字段（最多 10 个）：

```
标题 / 类型 / 来源 / 作者 / 原始链接 / 创建日期 / tags / 人物 / 事件 / 时期
```

`作者` 取 `data.author || meta.author`，而 `meta.author` 来自 `upstreamSourceMeta`
读来源节点的 `uploader`——**所以 UP 事实上已经在写了**，这是现状里唯一成形的维度。

**关键区分：快照 ≠ 知识库。** 前者按运行组织、无属性，是「这次交付了什么」的存档；
后者才可能被当成知识库。把 `outputs/` 直接当 vault 用，会得到一堆 `run_xxx` 目录平铺，
且笔记没有属性 → Bases/Dataview 一条都筛不出来。

### 2.2 缺陷清单（每条都能在代码里指到）

| # | 缺陷 | 证据 | 后果 |
| --- | --- | --- | --- |
| 1 | **一视频 ≠ 一笔记** | `resolveInputs` 把 N 段拼成 1 段（`join("\n\n")`），「Obsidian 笔记」只吃 `inputs.text` | 多视频被合并成一篇，「这篇属于哪个 UP」说不清 |
| 2 | **UP 只有名字，没有 mid** | `uploaderUid` 只出现在 `apps/server/src/routes/videos.ts` 与 `packages/shared/src/video.ts` 的 `VideoPreview`，**未写入来源节点** | 改名即断链；同名 UP 错并 |
| 3 | **议题维度缺失** | front matter 无议题字段；`extractHistoryEntities` 只提人物/事件/时期 | 第二个切面不存在 |
| 4 | **观点未结构化** | 「观点提炼」块产出的是 Markdown「观点块」 | 只能全文 grep，无法聚合 |
| 5 | **自动关联方向不对** | `findRelatedNoteNames` 只按 人物/事件/时期 打分，阈值 `score >= 3` | 时评/科技类内容无人物事件 → 永远 0 关联；且它是「笔记↔笔记」，不是「UP↔议题」 |
| 6 | **打标器是死代码** | `RunEngine.buildObsidianTags` 全仓 0 调用点 | 受控词表已设计但从未生效 |
| 7 | **文件名 = 标题** | `case "process.obsidian"` 的 `${escapePathName(title)}.md` | 不同 UP 的同名视频互相覆盖 |
| 8 | **属性名中英混用** | 中文键（标题/作者/…）+ 英文键（tags） | 社区反复警告的隐患：同一概念两个键名，查询结果不一致 |

第 1 条是最要命的：**原子性被破坏后，UP 与议题都无法唯一归属**，后面所有聚合都建在沙上。

## 3. 为什么「文件夹」和「字符串属性」都不行

**文件夹不行，因为它是单父级。** 一个视频同时属于「某 UP」和「某议题」，放进 UP 文件夹就丢了议题，
放进议题文件夹就丢了 UP，两边都放就得存两份并保持同步。Obsidian 官方立场与社区共识一致：
**文件夹管「物理归属/顺序」，多维度检索交给属性与链接。**

**裸字符串属性也不行，两个静默失败：**

- **改名即断链**：`作者: 某某UP` 是字符串。UP 改名后新笔记写新名、旧笔记留旧名，一次改名把时间线劈成两半。
  写成链接 `"[[某某UP]]"` 后，改名由 Obsidian 自动传播（这是 kepano 那套「category as link」的核心动机）。
- **同义写法分裂**：「外卖抽成」「外卖平台抽成」「平台佣金」若是三条字符串，则按议题聚合时会得到三张残缺的表，
  **且不报错**。这跟你们在别的项目里踩过的「探针值写错但流程不报错」是同一类陷阱：
  **聚合口径不统一 = 静默失真**。所以议题必须是**受控词表**，AI 只能「命中已有的」或「显式新建」。

## 4. 目标存储结构

### 4.1 目录（只按「卡片类型」分层，不按维度分层）

```
vault/
├── 视频/   2026-10-11 外卖平台抽成到底抽多少.md     ← 原子笔记：1 视频 1 篇
├── 观点/   外卖抽成过高-某某UP.md                   ← 原子观点：1 条观点 1 篇（第 3 层）
├── UP/     某某UP.md                               ← 维度一的实体笔记（hub）
└── 议题/   外卖平台抽成.md                          ← 维度二的实体笔记（hub）
```

### 4.2 视频笔记（双维度 + 唯一键）

```yaml
---
标题: 外卖平台抽成到底抽多少
类型: 视频笔记
来源: B站
UP: "[[某某UP]]"            # 维度一：写成链接，不写裸字符串
UP_ID: "12345678"           # 稳定 ID（B 站 mid）：改名不断链
议题:                        # 维度二：可多个，每个都是链接
  - "[[外卖平台抽成]]"
  - "[[骑手权益]]"
bvid: BV1xxxxxxxxx          # 稳定唯一键，用于去重与出处回溯
原始链接: https://www.bilibili.com/video/BV1xxxxxxxxx
发布时间: 2026-09-30
创建日期: 2026-10-11
tags: [未整理]
---
```

命名约定（建议）：**新增 `UP` / `UP_ID`，`作者` 保留原义（「这句话是谁说的」，供溯源用）**。
不复用 `作者` 承载 UP，是为了避开社区明确警告的「一个概念两个键名」——溯源配方里的「作者自述」
有可能是被引用者而非 UP 本人，两者语义不同。这个命名决定落地时应写进 `docs/decisions/`。

文件名建议 `{日期} {标题}.md`；撞名时（同标题）**用 `bvid` 兜底后缀**，而不是 `-2/-3`（后者不可读、不可回溯）。

### 4.3 观点卡（第 3 层，真正回答问题的那一层）

```yaml
---
标题: 某某UP：平台抽成过高，挤压中小商家
类型: 观点
UP: "[[某某UP]]"
议题: "[[外卖平台抽成]]"
立场: 反对                  # 受控枚举：支持 / 反对 / 存疑 / 中立 / 未表态
断言: 平台抽成过高，实际挤压了中小商家的利润空间
论据: 抽成 20% + 配送费 3 元，商家到手不足标价七成
出处视频: "[[2026-10-11 外卖平台抽成到底抽多少]]"
出处时间: "04:12"
创建日期: 2026-10-11
---
```

`立场` 用受控枚举是刻意的：它让「各 UP 对同一议题的观点」变成一张**可排序、可统计**的表
（几票支持、几票反对），而不是一堆自由文本。

### 4.4 两篇 hub 笔记 = 两个问题本身

`议题/外卖平台抽成.md` 里放一个 Bases 视图（伪代码，实际是 Bases 的 filter/列配置）：

```
WHERE 议题 == this.file.link && 类型 == "观点"
列：UP · 立场 · 断言 · 出处视频 · 出处时间
```
→ 打开这一页，就是「**各 UP 对该议题的观点**」表。

`UP/某某UP.md` 里放：

```
WHERE UP == this.file.link && 类型 == "观点"
分组：议题
```
→ 打开这一页，就是「**他对各类事情分别持什么观点**」表，按议题分组。

这两个视图**完全由 front matter 驱动，不需要插件代码**（Bases 是核心插件）。
选 Bases 而非 Dataview 的一个实际理由：坚果云/移动端场景下 Dataview 要每个 vault 装插件，
Bases 是内置的。

### 4.5 双链怎么来（把「相关」从打分改成确定性）

- **确定性链接**：视频笔记 → `UP` / `议题`（必然）；观点卡 → `UP` / `议题` / `出处视频`（必然）。
- 现有的 `## 相关笔记 [[...]]`（`findRelatedNoteNames`，人物/事件/时期打分）**保留**，
  但降级为「发现意外关联」的补充，不再承担主检索。主检索走上面两条确定性边。
- 因映射在属性里，Obsidian 的**反向链接面板自动**给出「谁引用了这篇 UP / 议题」，
  不用自己维护列表。

## 5. 落地改动清单（按性价比排序，分三期）

### 期 1：让双维度能聚合（结构性，最小可用）

| 改动 | 触及的符号 | 规模 |
| --- | --- | --- |
| 一视频一笔记：「Obsidian 笔记」按 `inputs.items` 逐项产出，替代吃 `inputs.text` | `engine.ts` 的 `case "process.obsidian"` | 中 |
| front matter 增加 `UP` / `UP_ID` / `议题` / `bvid` / `发布时间`；`议题` 写成 `[[链接]]` | 同上 | 中 |
| UP mid 落图：来源节点存 `uploaderUid`（数据已在 `VideoPreview`，只需透传） | `BiliSourceData`（`graph.ts`）、`biliSourceItemSchema`（`schema.ts`）、`bili-source.ts`、`upstreamSourceMeta` | 小 |
| 节点/设置里加「议题」输入口（手填 + 受控词表） | `ObsidianData`（`graph.ts` / `schema.ts`）、`ScribeNode.vue` 的 obsidian 分派 | 中 |
| 文件名改用唯一键（标题撞名时以 `bvid` 兜底） | `case "process.obsidian"` | 小 |
| 首次入库时生成 hub 骨架（`UP/`、`议题/` 不存在则建） | 新增小函数，`engine.ts` | 小 |

### 期 2：查询与受控词表

| 改动 | 说明 |
| --- | --- |
| hub 笔记模板内置 Bases 视图 | 纯模板文件，随 hub 骨架一起写 |
| 接通 / 重做标签与议题词表 | `buildObsidianTags` 是死代码：要么接线，要么删掉；`DEFAULT_TAG_TAXONOMY` 增「议题」类目 |
| 议题解析器（AI 返回 → 匹配已有议题 → 复用或标记新建） | 写入侧拦截同义分裂，这是正确性的关键，不是优化 |

### 期 3：观点层

| 改动 | 说明 |
| --- | --- |
| 新提示词块「观点抽取（结构化）」产出 JSON | 沿用现有配方机制（`recipe.ts` / `externalCheck` 那套 `items[].external` 回填模式），输出 `[{议题, 立场, 断言, 论据, 出处时间}]` |
| 观点卡写入器 | 按 JSON 逐条写 `观点/` 笔记 |
| 立场受控枚举 | 支持 / 反对 / 存疑 / 中立 / 未表态 |

**可测量的验收（结构性断言，不是效果指标）**：写入 N 篇后，跑一个检查断言
——front matter 的 `UP` / `议题` 非空率 = 100%，且 `议题` 值命中受控词表率 = 100%，
库内不存在同一议题的多种写法。这类断言应当进单测，因为**它一旦不成立，聚合会静默出错而不是报错**。
（这条对应你们既有的「前置断言 + 测量工具先自校验」规矩。）

## 6. 诚实清单

- **未验证**：本文没有做端到端运行（无 API Key），也没有在真实 vault 里跑过 Bases / Dataview 视图。
  §4.4 的视图是**按官方文档与社区实践的建模**，语法细节落地时需实测。
- **未验证**：Bases「一个属性值可指向多篇笔记」的数组 + 链接写法在具体过滤语法下的行为，
  以及跨文件夹 `WHERE 议题 == this.file.link` 的解析，均为调研结论而非实测。
- **简化**：§4.2 / §4.3 的字段集是**建议起点**，不是穷举；实际操作中还可能需要
  `系列`（合集/分P）、`时长`、`加工链路名` 等。
- **规模未估**：改动清单只给了相对规模（小/中/大），**没有工作量数字**——因为没有写下代码，给数字就是编。
- **已知会破坏兼容**：期 1 的「一视频一笔记」会让既有「Obsidian 笔记」工程从 1 篇变 N 篇，
  属于用户可见行为变更，落地时要进 `CHANGELOG.md` 并在 `docs/decisions/` 记录。
- **一处未决**：`UP` / `UP_ID` 是新增键还是复用 `作者`，本文推荐新增（理由见 §4.2），
  但这会与既有笔记的 `作者` 字段并存一段时间，迁移策略未定。
- **未做的事**：没有动任何代码，没有跑 `pnpm docs:gen` 之外的生成；本文本身不改变产品行为。

## 7. 主要来源

- Obsidian 官方 Bases（核心插件，v1.9.0，2025-05-21 起），Bases 只读 YAML 属性、不认行内 `key:: value`。
- Obsidian 论坛：Categories / Tags / Folders 三者定位与「category as bidirectional link」（kepano 做法）。
- 社区对比：Bases 提供可编辑的实时视图，Dataview 保留 `dataviewjs` 与行内字段能力；2026 年主流做法是「两者并存，Bases 做面板」。
