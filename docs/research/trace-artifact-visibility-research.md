# 同一枚卡、两类产物，怎么让用户看出来

> 触发：用户看着自己画布上两张并排的「AI 加工」卡（一张「观点提炼 · 速览版」、一张「信息溯源 · 上网查证」）问：
> 「这幅图所示状态对于一个用户来说，他完全会发生这样的事情……两个甚至还都是 AI 加工模块」。
> 日期：2026-10-16。
> 交付物：六套做法的可切换原型 [`trace-artifact-visibility-demos.html`](./trace-artifact-visibility-demos.html)
> + 逐套截图 `trace-artifact-{now,a-desc,b-badge,c-select,d-outlet,e-edge}.png`。**本轮没有改动产品代码**。

---

## 1. 问题不是「标题不清楚」，是**产物类别没有契约**

两张卡的**标题**其实已经写清了做法名（「观点提炼 · 速览版」/「信息溯源 · 上网查证」），描述行两张一模一样
（「使用提示词对文稿做 AI 加工」）。真正缺的是这条信息：**其中一枚的产物是另一类笔记**——
一片是普通笔记（`类型: 视频笔记/学习笔记`），一片是溯源报告（`类型: 溯源笔记`、会与同源笔记互链、
落盘前还要先由 JSON 转 Markdown）。

而这件事**系统自己也在猜**，且是两套猜法：结果页按**系列名**认（`isTraceBlock` 看「信息溯源」），
落盘那一步按**正文解析**认（`parseTraceReport`）。同一个事实两处各判一次，就是「两份实现会漂」的经典形态。

> 这一处缺口仓库里**早就记着欠账**：`docs/research/node-vs-prompt-block-boundary.md` 的「现在唯一欠的一处」写着
> 「让做法自己报一句『我做出来的是什么』……**没做、也没验证**」。当时是为结果页识别，现在同一个缺口在画布上又露了一次。

## 2. 调研：成熟产品怎么表达「同一枚节点、产物是另一类东西」

三条先例，都是「用**声明 + 徽章/类型**表达产物，而不是靠节点名字或内容嗅探」：

| 产品 | 做法 | 与我们的关系 |
| --- | --- | --- |
| **dbt** | 同一个「model」概念，`materialization`（`table`/`view`/`incremental`/`ephemeral`/`materialized view`）决定它产出什么；DAG 视图用**徽章 + 左侧色条**标出来（VS Code 的 dbt Lineage 扩展把配色列成了表：table 蓝、view 紫、incremental 橙、ephemeral 灰） | **最贴**：同一枚节点、产物种类不同 → 徽章表达。来源：[dbt Developer Hub `materializations`](https://docs.getdbt.com/docs/build/materializations)、[dbt Lineage 扩展](https://marketplace.visualstudio.com/items?itemName=Alshakarti.dbt-lineage) |
| **ComfyUI** | 端口**强类型**：`RETURN_TYPES` 声明每个输出口的类型字符串，**类型必须精确匹配**才允许连线（白名单策略），不匹配在运行前就被拦；端口同时按类型着色 | 说明「产物类别可以进契约」这条路的正规形态：类型进端口之后，连错线是**拦得住**的，而不是靠用户看。来源：[ComfyUI Custom Node Properties](https://docs.comfy.org/custom-nodes/backend/server_overview) |
| **n8n** | 节点的 `subtitle` 用表达式动态显示「这枚实例在做什么」（如 `Get: Contact`），官方的 ESLint 规则要求节点必须有 subtitle | 说明「副标题承载做法」是被平台方固化成规范的表达位。来源：[n8n Node Structure](https://mintlify.wiki/n8n-io/n8n/node-development/node-structure) |

三条加起来给出一套现成词汇：**做法声明产物（契约）+ 卡片上可见（徽章/副标题）+ 出口处可见（清单）**。

## 3. 五套做法与自量对照

原型页里六套（含现状）可切换，卡片照真机计算样式重画（320px 宽、标题 13px、描述 11px、
「联网核查」那一行只有声明了需要联网的提示词才有）。

| 做法 | 溯源卡高 | 出口卡高 | 产物类别在哪可见 | 顺便解决的 | 先例 |
| --- | --- | --- | --- | --- | --- |
| 现状（基线） | 219.9px | 140.7px | 看不到 | — | — |
| **A 描述行写产出** | 219.9px（**+0**） | 140.7px | 卡片描述行（11px，位置现成） | 声明可同时供结果页与落盘使用 | n8n 的 subtitle |
| **B 标题旁徽章** | 219.9px（**+0**） | 140.7px | 卡片标题右侧（`笔记` / `报告` 并排可比） | 同上 | dbt 的 materialization 徽章 |
| C 下拉项标产物 | 219.9px（+0） | 140.7px | 提示词下拉项（选择那一刻） | 同上（一处声明三处共用） | Zapier / n8n 的动作名 |
| **D 出口卡预告** | 219.9px（+0） | **223.4px（+82.7px / +59%）** | Obsidian 卡上「本次将写入 2 篇：观点笔记 + 溯源报告（互链）」 | 顺带回答「两篇进哪个目录」 | CI 的 artifact 预览 |
| E 连线标注 | 219.9px（+0） | 140.7px | 连线上（`笔记块` / `溯源报告`） | — | ComfyUI 的类型端口（它标的是类型不是文字） |

**A/B/C/E 一点高度都不占**（都是行内元素）；**只有 D 要付 +59% 的出口卡高度**——它换来的信息最多
（几篇、哪几篇、什么关系、进哪个目录）。

**关于缩放**：真机画布当前 zoom 是 **0.4636**（本次量卡片时读到的），那个尺度下标题本身只有约 6px、
本来就要放大才能读，所以新增的徽章/小字**不是新的可读性问题**——它和标题同命运。

## 4. 推荐：B + D，A 作为文案（C 顺带）

**推荐同时做 B 与 D**，理由是它们分别回答两个不同的问题：

- **B（标题旁徽章）回答「哪一枚会出报告」**——用户在画布上扫的时候要的就是这个，零高度成本，
  而且先例最贴（dbt 用徽章表达 materialization，正是「同一枚节点、产物不同」）。
- **D（出口卡预告）回答「库里会出现什么、它们什么关系」**——这是用户真正关心的事，
  而且它天然带出「两篇进哪个目录」这个现有信息（现在只能靠点开节点的高级设置才知道）。
- **A 不单独做，但作为 D 的文案来源**：描述行只有 11px 一行，写「产出：溯源报告（会与同源笔记互链）」已经接近挤满；
  所以把详细说明放在 D，卡片上只留徽章。
- **C 顺带做**（等确认 Element Plus 的下拉项能加右侧后缀），它服务的是「选择那一刻」，与 B 不冲突。
- **E 不推荐**：连线标注随画布缩放会一起变小、卡多了容易糊成一片，而它表达的「哪条线送的是报告」
  已经被 B（源头）与 D（出口）覆盖。

**但真正的前提在后端**：这三处显示都依赖**做法自己声明产物**这一个字段（`produces` 之类）。
不做这个声明，前端就还是靠系列名/正文解析去猜——也就是本文 §1 说的那个毛病。
所以落地顺序是：**先加声明，再让三处（画布徽章、结果页识别、落盘分派）读同一个声明**。

## 5. 诚实清单

- **原型是手画的控件**：卡片尺寸与配色照真机计算样式重画，但下拉、按钮不是 Element Plus 的真实渲染；
  落地要用 EP 组件（尤其 C 那处要确认能加后缀）。
- **「零高度成本」是量出来的**，但只量了高度——**没量视觉噪音**：一张卡上多一个徽章是否显得更乱，
  这件事需要人眼判断，我给不了数字。
- **D 的 +59% 是在 320px 宽的出口卡上量的**；如果用户把笔记节点收起了高级设置，出口卡更矮，比例会更大。
- **没验证 zoom 极小时（如 0.3）徽章的实际观感**：本文只说明「与标题同命运」，没有实测它在那个尺度下是否变成噪音。
- **没做无障碍检查**：徽章是纯色块 + 文字，读屏会连着标题一起念（「信息溯源 · 上网查证 报告」），
  这在语义上说得通，但没验过。
- **ComfyUI 那条只是先例、不是方案**：真要把产物类型做进端口，要动 `NODE_PORTS`（端口是节点类型级静态声明，
  不能按做法动态变类型）——那是比本文五套都大的改动，我没有把它当方案推荐。

## 7. 落地结果（同日，代码已改）

用户选了推荐组合 **B + D**（C 顺带）。落地的东西与本文 §6 的清单一一对应，但有三处**与原型不同**，
以及两处**顺手修掉的旧缺陷**：

**与原型不同的三处**
1. **声明不叫 `produces: "trace"` 而是 `PromptArtifact = "note" | "trace-report"`**，缺省＝普通笔记。
   自定义提示词一个字都不用改（它们永远拿不到声明，也永远拿不到配方——`builtin?.recipe` 只查内置）。
2. **结果页与落盘读的是同一句 `isTraceReportProduct(text, artifact)`**，而不是「只读声明」：
   声明优先，**产出方没声明时按正文格式兜底**（正文本身是一份可解析的报告 JSON 也算）。
   兜底是必要的——测试当场抓到：`source.text`（把一份报告 JSON 粘进文本来源）→ Obsidian 那条路
   没有产出方可以声明，只读声明会把整篇 JSON 原样写进笔记库。这条兜底与既有的
   `maybeDrillToMarkdown`（练习集 JSON 不许原样落进文档）是同一条下游规矩。
   **兜底不参与画布**：徽章与预告只读声明，所以普通笔记节点不会因为正文里恰好有一份报告 JSON 就被标成「报告」。
3. **`isTraceBlock`（按系列名判）已删除**，改由 `blockArtifact` / `nodeArtifact` 回答。

**顺手修掉的两个旧缺陷**（落盘那一步原先拿**整段文本**判报告，而不是逐份判）
- 关掉「每个输入一篇」把「报告 + 笔记」合成一篇时：整段解析不了 → 报告以 JSON 原样混进正文。现在逐份转换再拼。
- 两份报告合成一篇时：`parseTraceReport` 的兜底切片（第一个 `{` 到最后一个 `}`）跨了两份 JSON → 解析失败 →
  两份都落成 JSON。现在逐份转换。这条边界已写进 `packages/shared/src/trace.test.ts` 的用例注释。

**真机实测（Chrome CDP，无头，两个真实工程）**

| 量 | 实测 | 原型估的 |
| --- | --- | --- |
| 徽章对卡片高度的成本 | **0px**（溯源卡 251.9px → 藏掉徽章仍 251.9px） | +0 |
| 出口预告：两篇那张卡（1 笔记 + 1 报告） | 167.9 → 250.9px，**+83px / +49%** | +82.7px / +59% |
| 出口预告：五篇那张卡（5 份笔记） | 170.4 → 283.4px，**+113px / +66%** | 未估 |

量法：读**布局 px**（`getComputedStyle().height`，不受画布 transform 影响），一次只改一个变量
（先量原样，再给新增元素 `display:none` 后重量）。**原型估得很准**：它说预告块 +82.7px，实测 +83px。
比例上的差（+59% 对 +49%）来自分母——原型把「未改动前」画成 140.7px，实测是 167.9px。

> **量高度的尺子更正过（同日）**：这一节最初写的是 +70px / +96px，那是错的。
> 错因是归一化时拿错了缩放——先读 `.vue-flow__viewport` 的 transform（拿到 `none`，缩放不在那一层），
> 再退而按「卡片宽度 / 320」反推时又量到了另一枚节点。改用布局 px 之后复量，
> 数从 +70/+96 更正为 **+83/+113**，同时发现原型并没有高估（此前那句「高估约 15%」是错判，已删）。
> 同一把尺子后来用在 [`search-status-block-research.md`](./search-status-block-research.md) §4：
> 原型里「现状」卡量到 251.7px、真机 251.9px，差 0.2px。

真机断言 10/10 通过（`.tmp-cdp-artifact/verify.mjs`，跑完即删）：徽章文本（同屏一张「报告」、其余「笔记」）、
出口预告的篇数/逐条类别/互链句、五份输入的逐条列出、下拉项右侧后缀、以及**已有那次溯源运行**在结果页仍带「溯源」标记
且照常渲染阅读器（判据换掉之后没退化）。近景截图见
[`trace-artifact-landed-badge.png`](./trace-artifact-landed-badge.png)、
[`trace-artifact-landed-outlet.png`](./trace-artifact-landed-outlet.png)、
[`trace-artifact-landed-outlet-five.png`](./trace-artifact-landed-outlet-five.png)、

一个顺带的对账：五份输入那张出口卡上，预告写「本次将写入 5 篇」，同一张卡的运行摘要写「已保存 5 篇到 坚果云」——两者对得上。

**这一轮的诚实清单（接上文 §5，没解决的那些仍然没解决）**
- **视觉噪音仍然没量**：徽章高度是 0，但它看着是否显得更乱，只能靠眼睛——近景截图给了，判断归你。
  如果嫌吵，把「默认的笔记也标」改成「只标非笔记产物」是一行的事（`artifactBadge` 里加一个判断）。
- **只在两个缩放上量过**（0.75 / 0.59，都由卡片宽度反推），没量 0.3 那种极小尺度；卡宽固定 320px，所以换算本身可靠。
- **预告是照画布算的估算，不是引擎的承诺**：引擎真跑时若上游复用了历史产物、或某份输入是音频（会被排除），
  篇数可能与预告不同。预告的措辞一律是「本次将写入」，不是「已写入」。
- **没做色盲/无障碍检查**：徽章是纯色块 + 文字（「笔记」/「报告」二字本身承载语义），预告的「互链」句是灰字，
  对比度没量过。
- **没测极端画布**：一份笔记同时接进两张出口卡、或出口卡上游挂着条件分支（`flow.if` 的假分支）时，预告按连线的**静态**上游算，
  不看运行时分支结果。
