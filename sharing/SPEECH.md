## 逐页要讲的话

**P1 封面** — 一句话交代产品：把视频/文稿放进画布，用节点编排「转写 → AI 加工 → 合并 → 输出」，跑完得到一份笔记。今天不讲产品，讲它三个主体界面里最难做的部分。

**P2 三件事** — 强调这三个都是**用户看得见**的界面，不是工程配置。这点可以点一句：很多技术分享讲的是构建配置和 lint，那些东西用户永远看不到。

**P3 主题一过场** — 抛出核心判断：用了画布库，也不省产品级画布的工作量。5687 行里真正调库 API 的不到 200 行。

**P4 一个 nodeType** — 讲取舍，不讲实现。外壳共享换来 16 种节点复用；代价是外壳文件 2849 行、分派链 14 段。**要决策的是边界**：端口/菜单/状态/只读该共享，具体表单该拆。补一句 Vue 的坑：节点组件必须 `markRaw`，否则会被包成响应式代理。

**P5 端口类型** — 讲「连线合法性由类型系统决定，不由界面决定」。4 种端口类型 + `noteDoc` 收 `noteBlock` 的偏序 + 三道关卡。**主动讲那句诚实的**：这条规则现在有三份实现，其中一份已经不认多类型端口、只在测试里用。

**P6 撤销重做** — 先讲机制（快照、50 步、剥掉运行态、逐字改图 + 失焦提交），再讲两个副作用。副作用那段是全场最容易共鸣的地方：用户按 Ctrl+Z 觉得没反应，因为压入了重复快照；撤销顺带把镜头弹回去，因为视角也在快照里。

**P7 浮层坐标系** — 技术含量最高的一页，也是最容易讲出「原来还有这一层」的一页。顺序：先说问题（浮层传送到 body，脱离缩放坐标系）→ 解法（provide 一个 zoom，浮层用 CSS zoom 补偿）→ 三个细节（位置不用补、只有尺寸要补、用 zoom 不用 transform）→ 最细的一处（屏幕宽度要除以缩放才是节点局部宽度）。收尾点一句 provide/inject 能穿过 Teleport 是 Vue 的机制红利。

**P8 主题二过场** — 交代场景：转写和 AI 加工可能跑很久，而且中途断线、切页面、服务重启都是常态。

**P9 有了推送反而更需要轮询** — 本场的核心反直觉点。**一定要讲透**：直觉是有推送就不用轮询，而这里反过来——推送是唯一会静默失效的通道，断线、丢帧、服务重启它都不报错，只是不说话了。所以数据库是真相通道，推送只是加速通道，轮询是它的正确性校正器。四层兜底逐条念。

**P10 建连即补快照** — 讲清因果：广播是内存集合，没有重放缓冲（运行结束 60 秒后就没了），所以「连接」这个动作必须自带状态同步。四类节点分别补什么，一句话带过。

**P11 放弃增量** — 讲清那个取舍链条：增量要求「先收到全部前置事件」→ 于是重连必须做事件重放 → 而这套系统没有重放缓冲 → 路走不通。换成全量覆盖后重连正确性问题直接消失，顺带解决了大图重渲染。

**P12 局部重跑是新运行** — 讲因果链：新 run id → 结果只含本次范围内的节点 → 画布上其它节点退化成未运行（视觉上像删了之前的成果）→ 视图层从历史运行回填。结论那句要念：把复杂度从「前端状态机」挪到了「纯函数式的快照合并」。

**P13 主题三过场** — 交代矛盾：一张卡挂 8 个视频，引擎把它们拼成一份，人却要一个一个读。

**P14 拼起来 vs 按段读** — 讲为什么能还原：靠运行时记录的「每个输入一行」反推，所以**历史运行不用重跑就能分段**。标题要向上游回溯最多 12 层取视频名，这是「让派生数据可推导」比「让后端多存一份」更划算的例子。

**P15 AI 产物坏了是常态** — 三个手法一起讲最有说服力：逐条丢弃但原因必须是人话、生成期严展示期松（不判两次死刑）、类型靠嗅探且要互斥（曾经把练习题渲染成空的溯源表，这个真实 bug 讲出来很加分）。

**P16 可视化库的成本在时序** — 讲 markmap 的四个坑：0 尺寸不初始化、实例建好再喂数据、关掉 autoFit 只适配一次、首帧隐藏到就绪。最后那个版本坑要讲：该版本的 JSON 配色选项会让整张图渲染空白，所以颜色改走 CSS 变量。

**P17 三个判断** — 逐条念，可以请大家一起念第一条。

**P18 我们没做好的三件事** — **不要跳过**。这三条都是我自己在代码里核出来的：提示抛了没人接、同一规则三份实现、状态机比契约小一圈。主动讲缺陷会显著提高整场的可信度。

## 大概率会被问到的

> 被问「你们中间遇到什么问题、怎么解决的」时，照 [QA.md](./QA.md) 答——那里按
> 「现象 → 怎么定位 → 结论与改法 → 证据强度」记着实际查过的问题，每条都标了数字是实测还是推断。

- **「为什么用 Vue Flow，不自己写或者用 React Flow？」** — 技术栈是 Vue 3，React Flow 是 React-only。但换了库也不省事：5687 行里真正调库 API 的不到 200 行，其余（表单、端口类型、撤销、只读、缩放补偿、持久化护栏）都得自己写。
- **「局部重跑为什么不复用旧运行？复用了就不需要合并了。」** — 复用会破坏「一次运行的审计边界」：这次跑出来的算哪次运行？耗时怎么算？现在的做法是把复杂度从前端状态机挪到纯函数式的快照合并。
- **「为什么不直接让后端返回分段数据？」** — 分段是能从既有事实推导出来的（运行时记录了每个输入一行），让它可推导比多存一份更划算，而且历史运行也能立刻分段。
- **「AI 返回的 JSON 不合法怎么办？」** — 三层降级：裸 JSON → 去代码围栏 → 截首尾大括号；再不行就逐条丢弃并给出原因，绝不让一条坏数据毁掉整批。
- **「几百个节点会不会卡？」** — **没有测过**。仓库里没有前端性能基准，这是个已知缺口。已知的两个隐患是深响应式数组每次事件全量 map，以及快照恢复时逐节点重建对象。
- **「撤销弹镜头不能改吗？」** — 能，把视角移出快照即可，代价是撤销后视角不动、可能看不到被改的节点。
