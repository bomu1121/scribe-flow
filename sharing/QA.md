## 一、四条真正查过的问题（可以直接讲）

### 1. 用了「素材挑选」之后，结果页的段标题会指错视频

**现象。** 八个视频经过同一条转写链路时，结果页会把它们切成八段，每段带原始视频的标题与 UP 主。
一旦链路里加了「素材挑选」跳过其中几段，**正文是对的，标题和时长却指向没被选中的视频**。

**怎么定位的。** 写了个探针，按引擎的真实行为构造输入：四个视频的 B 站卡片 → 转写 → 挑选（只保留第 2、第 4 个）→ 输出，
然后调用真实的 `buildNodeSegments`。输出是：

```
段 1  标题="第一个视频"  meta="UP主 · 1:40"  正文首行="# 视频二笔记"
段 2  标题="第二个视频"  meta="UP主 · 3:20"  正文首行="# 视频四笔记"
预期 ["第二个视频","第四个视频"]，实际 ["第一个视频","第二个视频"]
```

**根因（三处叠加，每处单独看都合理）。**

1. 引擎在挑选过滤之后**把 position 重新编号**：`apps/server/src/lib/engine.ts` 的 `resolveInputs` 里
   `const resolved = kept.map((item, i) => ({ ...item, position: i }))`。被跳过的位置被补齐了。
2. 但身份其实**没丢**：`engine.ts` 的 `flow.pick` 分支把 `itemKey` 原样传给下游。这一处是对的。
3. 前端解析时**完全不看 itemKey**：`apps/web/src/utils/run-segments.ts` 用「数行数」得到来源序号
   （`indexWithinSource`），再拿它去索引来源卡片的完整条目数组 `items[sourceIndex]`；
   向上游回溯那条链也靠 **position 相等**匹配。序号一被重编号，两处一起偏。

**改法（两条路，建议第二条）。**

- 前端路：段上带 `itemKey`，用它做身份——匹配上游、解析来源序号都用它。
- 数据路：**落库时就把来源引用写进 `run_node_inputs`**（如 `originNodeId` + `originItemIndex`，或直接存标题）。
  引擎写这一行时是知道身份的；而"向上回溯最多 12 层"这套推导，就是为了省这个字段付的复杂度，现在还推错了。
  这个字段一加，`resolveSegmentLabel` 与 `resolveSegmentMeta` 两段回溯可以整体删掉。

**一条必须守住的约束。** 不要只改 `position` 的语义：日志的 `input.index` 注明对应 `run_node_inputs.position`，
动它会连带影响日志归属。

**影响面与现状。** 这个函数被四处共用：结果页、画布节点预览、日志弹窗、它自己的测试。
**现有演示工程不会触发**——`【演示】素材挑选` 用的是三个 `source.text`（单份、无身份）；
要「B 站多选 / 收藏夹（多条目）+ 挑选」这个组合才会撞上，而那正是最近一次提交在做的那条线。

**证据强度。** 探针复现，实测。**没有**在浏览器里端到端复现（需要一条真实的「多选 + 挑选」运行记录，要联网、下载、ASR）。
"三处界面都会显示错标题"是从调用方推出来的。

### 2. 分段重建接近平方复杂度

**现象。** 结果页要按段渲染，段是从运行时的输入行推出来的。输入行一多，这个推导会变慢。

**实测数字**（本机 Node 22，纯函数耗时，三次取中位）：

| 规模 | `buildSegmentMap` 耗时 |
| --- | --- |
| 40 行（5 节点 × 8） | 0.1 ms |
| 200 行（10 × 20） | 1.4 ms |
| 1000 行（20 × 50） | 15.2 ms |
| 3000 行（30 × 100） | 160.5 ms |

行数涨 7.5 倍，耗时涨约 1600 倍 → 接近 O(n²)。

**根因。** `resolveSegmentLabel` 与 `resolveSegmentMeta` 在每一段上跑一个最多 12 层的循环，
每层对全部输入行做一次 `rows.find(...)`，还要对节点做一次 `graph.nodes.find(...)`；
`buildSegmentMap` 又对每个节点跑一遍 `buildNodeSegments`。

**为什么现在就该管。** 它被放在 `computed` 里用，运行中每来一个 SSE 事件 `run.inputs` 都会变，
整个重建就重算一次。1000 行 15 ms 已经落在掉帧区间。

**改法。** 约 10 行：进函数先建两个索引表（`byTarget + position`、`nodesById`），把循环里的 `find` 换成查表。
若第 1 条走了数据路，这段逻辑可以直接删。

**证据强度。** 实测（本机，纯函数，不含 Vue 响应式与渲染开销，真实页面只会更差）。

### 3. 从节点面板连续添加，节点会像素级重合

**现象。** 面板里的提示是「点击添加到画布中心」。连点三次加三种节点，屏幕上只像多了一张卡片。

**实测。** 三个节点的 DOM `transform` 完全相同（`translate(626px, 426px)`），
服务端保存的 `position` 也全是 `(626, 426)`。位置不是"接近"，是同一个坐标。

**后果。** 用户看不出自己加了几个；新人第一次上手就会撞上（这是照最自然的操作路径走出来的）。

**改法方向。** 添加时按已有节点做一个递增偏移（n8n 就是这么做的），或加完自动进入"适应视图"。

**证据强度。** 实测，且服务端数据可查。

### 4. 「一个输入一份结果」这条规则散在三处代码里，语义还各不相同

这个项目有一条核心业务规则：哪些节点「一个输入一份结果」，哪些是「压平型」。
实现上它在三个地方各写了一份，而且三份的语义并不一样：

- `packages/shared/src/segment.ts` 的 `PER_INPUT_NODE_TYPES` —— 判断「身份能否穿过该节点」（挑选链用）
- `apps/web/src/utils/run-segments.ts` 的 `PER_INPUT_RESULT_TYPES` —— 判断「结果从哪里取」（结果页用）
- 同文件的 `SECTION_TYPES` —— 判断「哪些是压平型」

外加 `AGENTS.md` 硬规则第 6 条与 `docs/nodes.md` §1.2 的文字版，共五处。

**这不是我推断的**：`run-segments.ts` 里有一段注释明确写着「**不能**改用 shared 的 `PER_INPUT_NODE_TYPES`，
两者语义不同」。这个判断本身是对的，但它同时说明：同一个业务概念被表达成了三套代码，
新增一个节点要同时改五处，漏一处就是静默的行为差异（第 1 条那个错位就发生在这一带）。

**改法。** 在 shared 里放**一张表**，每个节点类型一行，用字段表达各条语义
（能否被挑选穿透 / 结果取自身输入还是下游 / 是否压平），三处消费者全部从表里读。加新节点只改一行。

**证据强度。** 三处代码实现与两处文档描述都是 `grep` 出来的，不是估算；
"语义不同"这一判断来自你们自己写在 `run-segments.ts:34` 的注释。

## 二、这个模块做对的地方（被追问时主动讲，比只讲缺陷可信）

- **AI 产物进 DOM 之前做了清洗。** `apps/web/src/lib/markdown.ts` 用 `marked` 渲染后过一遍
  `DOMPurify.sanitize` 再插入（同时给标题补 id 供目录跳转）。这类产品最容易漏的一处，没漏。
- **单输入不分段。** 只有真的存在两份以上内容才返回分段（`contentful.length < 2` 就返回空），
  不给单输入节点多套一层没有意义的选择器。
- **分段靠运行时记录反推，所以历史运行不用重跑也能分段。** 实测你们 9 月 13 日那条运行
  （B站 → 转写 → AI 校对 → AI 加工 → 输出，耗时 132.6 秒，产出 6284 字），打开就是分好段的。
  这个取舍（可推导 > 多存一份）在**推导无歧义**时是对的；它失效的边界就是上面第 1 条——
  一旦上游把序号重新编号，推导就不再有唯一答案。
- **挑选把素材全排除时直接抛错**（"素材挑选没有选中任何素材：共 N 段全部被排除"），
  不静默产出一份空笔记。

## 三、我自己踩的测量坑（被问「你的数字可信吗」时最好用）

### 5. 用错的分辨率，量出了一个不存在的结论

我一度断言"节点卡片太大，一屏放不下两张"。真实情况是：我当时把测试视口设成 1600×900 与 2200×1000，
而对方显示器是 **3840×2160**（画布区 3492×2112）。
卡片在源码里是 **320–380 px 宽**（`ScribeNode.vue` 的 CSS：224 / 320 / 340 / 380，按节点类型），
只占那块画布宽度的约 **10%**，一屏能放**十来张**。

根子在于：我量的是**屏幕像素**，却没有控制**画布缩放**（当时画布被放大到 2.6 倍、后来是 4 倍）。
屏幕像素 ÷ 缩放才是卡片尺寸——这一步我漏了。

**可复用的教训：凡是"看起来太大/太小"的结论，先写下两件事——视口尺寸与缩放倍率。** 缺一个，结论就不成立。

### 6. 把一个环境问题报成了产品缺陷

界面上出现过 4 到 6 条一模一样的「操作失败 / 请求失败（500）」，堆着不消失。
我当时把它列进了产品问题清单。后来的证据指向环境：前端显示的是兜底文案「请求失败（500）」，
而**只有响应体里没有 error/message 字段时才会走到这个兜底**——也就是说这个请求根本没到达应用自己的错误处理
（应用层的错误一定返回 JSON）。之后 50 次经代理的请求、3 次页面内调用全部 200，复现不了。

**教训：报错长什么样本身就是证据。** 兜底文案 = 请求没到应用；带中文原因的 = 应用自己抛的。这两个要分开归因。

### 7. 差点把一个不存在的缺陷报出去

讲稿里写「契约里 7 个节点状态」。我在 `packages/shared/src/run.ts` 数到 `NodeResultStatus` 只有 6 个成员，
准备判定讲稿写错了。再查一层才发现画布侧另有一个 `NodeRunStatus`（`packages/shared/src/graph.ts`），
含 `idle` 正好 7 个。**是我只查了其中一个类型。**

**教训：同一个业务概念在多个包里各有一份类型时，"数一遍"不算验证，要先找齐所有定义。**

### 8. 想做成「复制了链接就自动建工程」——先量错两次，最后发现是浏览器不给

**我想做什么。** 现在的入口是：点「粘贴链接建工程」→ 对话框打开时自己去读剪贴板 → 回车。
想省掉那一步——像游戏识别卡组代码一样，你在别处复制了链接，这边自己认出来、自己冒出来。

**怎么查的。** 用真实 Chrome（152）+ 真实的系统剪贴板跑探针，把读取和复制都放进页面自己的脚本里执行，
脚本只负责看日志（不走调试通道的特权路径，避免量出假成功）。跑了三版，前两版结论互相矛盾：
第一版说「在别处复制、切回来会补发一次通知」，第二版说「不会补发」，
两版都测出「一次复制产生 3 条通知」。

第三版才找到根因：**我用脚本设剪贴板的那一步，本身会把浏览器挤到后台。**
探针里那些失败有很大一部分不是产品行为，是我的测量动作造成的。
第三版改成让页面自己发起复制，并且每一步都先把页面拉回前台、把焦点值打出来（拿不到焦点就把这条样本作废），数字才稳定：

| 场景 | 实测 |
| --- | --- |
| 全新状态（没点过、没读过），页面在前台，改剪贴板 | 变更通知 **0 条** |
| 真实点击过一次后（仍未授权），改剪贴板 | 变更通知 **0 条** |
| 页面在前台时首次读剪贴板 | **成功**，权限由「待询问」变「已允许」 |
| 页面不在前台时读剪贴板 | **直接报错**：`Document is not focused` |
| 已经允许过之后，页面自己复制一次 | 变更通知 **1 条**（先前测到的 3 条是脚本设剪贴板的多步写入造成的） |
| 已经允许过之后，在别处复制 → 切回页面 | 补发 **1 条**通知 |
| 切回前台后读剪贴板（权限还没允许过） | **成功** |

**结论：这个交互在网页里做不到——不是难，是不允许。** 两条硬约束：

1. **页面得在前台才让读。** 而用户复制链接的那一刻，页面恰恰不在前台：他在 B 站 App 或另一个标签页里。
   所以「复制完它就自己冒出来」在网页里不存在，怎么轮询都一样。
2. **没有"剪贴板变了"的通知可以被动听。** 什么都没允许过的状态下实测 0 条通知，点过一次也还是 0 条。
   游戏客户端能做这件事，是因为它是桌面程序，剪贴板是系统资源，随便轮询。

**顺着能讲的一条。** 唯一可行的近似形态是两段式：先用一次用户操作换来权限（现在那个按钮就干这个），
之后再挂上通知监听——此后用户切回页面时，若剪贴板里是链接，可以弹一条「检测到链接，一键建工程」。
**不是自动，是"用一次点击换来的自动"。**

**决定：不做。** 顺带实测出一个正面结论：这个入口比它自己注释里担心的更可靠。
注释写的是「权限被拒（非安全上下文/未授权）就静默降级」，但 `127.0.0.1` 实测是安全上下文，
点按钮打开对话框那条路径首次就能读到，不用先授权。

**教训：当你要测的东西本身会改变被测环境（这里：设剪贴板会把浏览器挤到后台），
每条样本都要把前置条件打出来，条件不成立就作废。**
否则你会拿着伪影下结论——而且换一种做法能得到相反的结论，两次都看起来像真的。

**这条的局限。** 都在本机 Chrome 152 上测的，没测 Edge / Firefox / Safari
（后两者不支持「剪贴板变更通知」这条来自资料，不是实测）；「已允许后切回补发 1 条」是单次观测（n=1），
没有重复；「真实点击」是脚本模拟的点击，是否等价于真人点击没验证，
所以「点过一次不够」只能说**没观察到触发**，不能说已经证伪；
也没在 app 自己的端口上跑过——这个权限是按站点分别授予的，`127.0.0.1:5173` 会独立走一遍。
「没弹权限框」是推断（依据是权限状态在无人操作的情况下由「待询问」变成了「已允许」），没有直接观测到弹框与否。

**台上一句话版。** 「我本来想让复制链接这一步也省掉，像游戏识别卡组代码那样。
查完发现网页做不到：浏览器规定页面得在前台才准读剪贴板，可你复制链接的时候，我的页面正好不在前台。
这一条不是技术不够，是平台不让。顺带发现我自己前两次量错了，因为测试脚本设剪贴板的动作会把浏览器挤到后台——
我以为测出来的是产品行为，其实是我自己造成的。」

## 四、观测到但还没结论的（被追问时如实说）

- **删除节点后刷新，节点会回来。** 见过两次。一次是逐个选中按 Delete 之后、界面显示"已保存"、
  服务端仍留着 1 个节点；另一次我没有删任何东西，节点却从画布上消失、刷新后又回来。
  但我的操作是合成点击，而且第二次时画布缩放已被我的操作改到了 4 倍，**所以我不能断言这是产品缺陷**。
  建议用真实鼠标复现一次再定性。你们代码里已经为相邻方向的竞态留了注释与备份
  （`apps/server/src/routes/projects.ts` 里"编辑器在异常路径下可能把空画布写回来"），这条值得顺着看。
- **报错提示会堆积且不自动消失。** 触发一次错误后出现 4–6 条相同内容，跨页面跳转都还挂着，只能手点关闭。
  和上面第 5 条的成因分开：提示的堆叠与否，与 500 是谁造成的无关。
- **空工程没有任何引导。** 0 节点的画布是一张空白网格，没有任何"从左侧节点面板拖进来"的提示；
  唯一说明藏在「节点」面板顶部。这条在 3840×2160 下复核过，与分辨率无关。
- **挑选的空数组语义。** `passesPick` 里空数组对**有身份**的条目是"全部排除"，
  对**无身份**的条目（如 `source.text` 的整篇）却是"全部放行"（`if (!itemKey) return true`）。
  演示工程里存的 `pick: {"n_2":[]}` 因为来源都是 `source.text`，看起来像"一个都没选"实际全部放行。
  代码语义已确认，UI 怎么呈现 `[]` 未确认。

## 六、另外一条线：仓库文档为什么会把工具带偏

这条与产品无关，但如果被问到"你怎么让 AI 工具在这个仓库里干活"，可以讲：

一次评审中，工具给出的问题清单几乎全部来自仓库自己的 `docs/status.md` 缺口表与讲稿的"没做好的三件事"，
它把仓库的**自我批评叙述**当成了项目的问题清单，而没有去看产品本身。查外部证据后确认这不是个案：
有对照实验显示，给 agent 一份权威口吻的过期文档后，它主动去核对的行为会被压住
（被"积极误导"比例 68–100%，任务成功率跌到 0–32%），而**新鲜文档同样会压住核对行为**——
文档不是补充信息，它**替代**了 agent 去核对的动作。

处置：仓库的两扇正门（`AGENTS.md` 与 `README.md`）重写了一遍，讲产品的内容从 5 行扩到 31 行，
讲文档治理的内容从 66 行压到 17 行；保留的是推断不出来的东西（许可证红线、颜色令牌、
`tsx watch` 在 `pnpm dev` 下会静默挂住、数据库只能加列、`knip` 不能升到 6）。
完整调研与证据分档见 [../docs/research/repo-legibility-and-over-engineering.md](../docs/research/repo-legibility-and-over-engineering.md)。
